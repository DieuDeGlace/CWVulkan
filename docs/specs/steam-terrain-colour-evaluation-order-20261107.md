For a nonzero voxel reached by the final scan in ordinary terrain mesher RVA 0xE9530, block type and base colour are evaluated before the individual face-exposure decisions. A fully blocked voxel reached by that scan can therefore still execute base-colour work. Corner occlusion/light evaluation, vertex packing and index emission are inside the admitted face paths. These statements describe the reached native scan, not every hidden voxel in the World or an unconditional coordinate-only colour function.

The supported image is original x64 Steam binary/cubeworld.original.exe.unpacked.exe, preferred base 0x140000000, PE timestamp 0x5D93AB0D, SHA256 7AF18CB28C8BF848F355287428C6390B2EA2A682CA466190F5EB9859C5D6F244. The image hash was checked for this audit. Evidence consists only of the individually identified original routine files in decompiled/functions, address-scoped original decompiled/assembly.txt, and constants read from that image. All native addresses below are RVAs. This is a CPU evaluation-order contract; shader evaluation, mesh publication, lifetime and broader generation are outside its scope.

Preparation precedes colour emission. At 0xE96F2 the mesher calls light-preparation routine 0x2A3260 after constructing the neighbourhood/light working storage through 0xCB9C0. That preparation is before both the exposure/bounds scan and the later vertex scan. It builds and propagates byte light values in the working tables. It also has a reached write-back phase: for stored voxel records whose type is 0 or 2, it replaces record byte 0 with the computed light byte and calls record writer 0xA36E0 at 0x2A3D95. The other copied record bytes are retained at this site. This is an actual voxel-data write, not merely a temporary corner-light calculation. The propagation algorithm and its full protection/lifetime contract are not re-audited here.

The earlier exposure/bounds scan reads the current voxel and neighbour types through 0xDA660, beginning with the call at 0xE9AA8 and the following directional reads. It does not call material-colour routine 0x2D8E00, corner-light routine 0xE8F70 or packer 0xC3A10 at those tests. Its result is used in constructing mesh-group working ranges. It does not turn the final scan into a list containing only exposed voxels. The final scan independently reads column and voxel data again.

The final ordinary column traversal increases world X, then world Y, and increases the signed 32-bit height within each examined column interval. Column lookup 0xDFB50 supplies the stored column, including its signed 32-bit start at +0x3C and six-byte-record array at +0x40/+0x48. The inspected interval starts one height below the minimum available start of the current and four horizontal neighbouring columns and normally continues below the current column's end. A later reached branch can extend a column ending below height 1 through height 0. Missing columns and samples outside these reached intervals are not assigned any colour-evaluation obligation by this contract.

At 0xEA1DE, the final scan obtains a six-byte current-voxel record through 0xDA660. Its type is the unsigned byte at record offset 4, saved at 0xEA1E3. Type 0 branches past base-colour and face work at 0xEA1EC. For a nonzero type, the comparison at 0xEA1F2 also records whether the type is 0x14, which later selects the corner-light bypass. The first three record bytes are converted as unsigned RGB components to 32-bit floats, an alpha component of 255 is supplied, and all four components are divided by the image constant 255 before any directional face query. The stored record's byte 3 is not substituted for this base alpha.

Below the current stored column's start, the height comparison at 0xEA261 admits additional procedural base-colour work. The mesher calls 0x2D8E00 at 0xEA325, then 0xBA820 at 0xEA334. For finite RGB values, 0xBA820 halves each returned component, clamps it into the interval from 0 to 255, truncates it to an integer and retains its byte value. It also copies the returned three metadata bytes into its temporary six-byte record. The mesher then converts only those resulting RGB bytes back to floats, again with alpha 255 and division by 255. The current type saved from the first accessor remains the type controlling water routing, the 0x14 bypass and face admission; the procedural result's type metadata does not replace it at these sites. No procedural colour result is written back to the source column by this sequence.

There is a separate condition on refreshing the procedural inputs. At 0xEA0C5 the minimum available column start must be strictly below the current column's start before the branch loads the current column's parameter fields and calls neighbour-parameter routine 0x35EA0. Those calls occur in negative-X, positive-X, negative-Y, positive-Y order at 0xEA12D, 0xEA148, 0xEA163 and 0xEA17B. The later below-start colour call has its own height test and lies outside that refresh branch. It is not guarded by face exposure. This audit does not prove fresh equivalent per-column values for every otherwise hidden below-start trial when the refresh branch is skipped, or turn the retained argument state on such a path into an invented default.

The ordinary directional face queries then occur in negative-X, positive-X, negative-Y, positive-Y, negative-height and positive-height order, at 0xEA464, 0xEA8A5, 0xEACF2, 0xEB153, 0xEB5A2 and 0xEB9DD. For a current non-water nonzero type, a neighbour type of 0 or 2 admits that face. For current water type 2, only neighbour type 0 admits it. These are separate reads at their positions in the traversal, not one precomputed six-face exposure record.

Consequently, for a reached non-water nonzero voxel whose six tested neighbours are all neither type 0 nor type 2, the normalised stored base colour, and any admitted below-start procedural colour conversion, have already happened. None of the six face bodies executes its corner-light, pack, append or quad-index calls. A voxel with some admitted faces runs those operations only for the admitted faces, in the directional order above. This is a statement about the actual sequence of reads; it does not assume that live neighbours remain unchanged between the separate reads.

Each ordinary admitted quad evaluates its four corners sequentially. For each corner it first calls 0xE8F70, immediately packs that returned four-float result through 0xC3A10, and immediately appends the eight-byte packed vertex through 0xE2D00 before evaluating the next corner. The first negative-X face demonstrates the complete order: its four corner-light calls are 0xEA550, 0xEA64A, 0xEA74A and 0xEA845, followed individually by pack calls 0xEA56D, 0xEA667, 0xEA767 and 0xEA862. Its quad-index call is later at 0xEA881. The other directional bodies use the same per-corner sequence. There is no per-voxel call that computes all corner colours before the face tests.

For ordinary non-bypassed corner evaluation, 0xE8F70 uses the supplied corner's world coordinates, the selected cardinal direction, the neighbourhood voxel accessor and the prepared byte-light tables. Its neighbour loops visit X offsets first, then Y offsets, then height offsets. For a cardinal direction this is one sample position on the directed axis and six positions on each transverse axis, giving 36 queried sample positions. Types 0 and 2 qualify as open/light-sampling space. The routine separately accumulates weighted openness and a weighted light-byte average. It applies the literal power 1.2 to openness before its RGB adjustments and final RGB clamping, and puts the weighted light average divided by 255 into the fourth output component. Thus this fourth component is calculated corner light on this path, not the original base alpha. The reads are per call and may be repeated for adjacent corners.

A nonzero bypass argument takes the short copy path at 0xE8FA6 through 0xE8FC1: it copies all four supplied base-colour components to the output without the neighbour/light-table loops. In the ordinary terrain path this argument was selected from current type 0x14 before face testing. Such an admitted face still calls the helper, packer and append routines for each corner, but its helper does not do the ordinary occlusion/light work. Fully blocked type-0x14 voxels still have no face-body corner calls.

Packer 0xC3A10 writes an eight-byte record. It retains the low byte of each of the three supplied 32-bit position components, records the cardinal direction code, then stores four colour/light bytes. For the ordinary cardinal inputs, codes 0 through 5 identify positive X, negative X, positive Y, negative Y, positive height and negative height. Each supplied float component is multiplied by 255, truncated to a signed 32-bit integer and narrowed to one byte. The packer adds no second clamp. This conversion reads no World or light cache and has no advancing random draw in its inspected body; its result is determined by its supplied arguments and the literal conversion constant for the finite, representable inputs described here.

After all four packed vertices, 0xCD7D0 computes each opposite-corner difference using the already packed RGB bytes and the image luminance weights 0.299, 0.587 and 0.114. It chooses between the two triangle diagonals by the absolute differences; equality selects the diagonal joining the second and fourth appended corners. It does not use the fourth packed component in that choice. Colour quantisation therefore precedes this index-order decision. The vertex/index append routines mutate their working arrays and may grow their storage. The local base-colour and corner-light calculations are distinct from those append side effects.

Ordinary water type 2 first passes the nonzero-record base-colour sequence, then overrides its four base components at 0xEA3CD with the image literal at 0x43F0E0: red 0.25, green 0.5, blue 0.5, alpha 1. Water routing and the whole-sea suppression check follow that override. Ordinary admitted water faces still perform four corner-light, pack and append operations. For these water faces the direction supplied both to corner lighting and packing is positive height even for a side or bottom face; it is not the non-water face's geometric cardinal direction. Water does not receive the type-0x14 bypass. Its corner-light fourth output component is calculated from the light table as above.

The whole-zone sea quad is a distinct earlier path. After the vertical-range precondition, its qualification reads all 64 by 64 columns, requiring type 2 at height 0 and record byte 0 equal to 255 at height 1, through the calls at 0xE9D3C and 0xE9D63. The latter test is a byte test; this contract does not silently replace it with an air-type test. The four whole-zone vertices at height 1 directly pass the same literal RGBA to packer 0xC3A10 at 0xE9E19, 0xE9E75, 0xE9EDA and 0xE9F3C, each followed by append. There are no intervening 0xE8F70 corner-light calls for this quad. With the proved truncation, its four packed colour bytes are 63, 127, 127 and 255. It is packed before the later ordinary column scan. When this path qualifies, the later water-type-2 sample at height 0 still reaches base-colour/override work, then skips its ordinary six-face emission; this does not suppress other water heights.

The type-3 upper-surface film is another distinct path. After the positive-height face query admits the top surface, current type 3 causes a second upper-voxel read at 0xEBA21. Only a type-0 result on that second read admits the film. The film uses the fixed water RGBA and positive-height direction, runs four corner-light calls at 0xEBAC8, 0xEBB87, 0xEBC46 and 0xEBD03, packs/appends each result and emits its water-index quad at 0xEBD3E. The ordinary terrain top face follows, using the terrain base colour, with its corner calls at 0xEBDDA, 0xEBE8B, 0xEBF3C and 0xEBFEB and its quad-index call at 0xEC01F. Thus the film is emitted before the terrain top face. The second type test is part of the native order; no wetness-flag interpretation or stable repeated-read assumption is added.
