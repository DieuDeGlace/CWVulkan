# Steam conversation generation: native ABI, ownership, and protection

This bounded native-only note supports the original unpacked image cubeworld.original.exe.unpacked.exe, 5,757,952 bytes, SHA-256 7AF18CB28C8BF848F355287428C6390B2EA2A682CA466190F5EB9859C5D6F244. Its PE machine is AMD64, optional-header format is PE32+, and preferred image base is 0x140000000. Addresses below are RVAs relative to that base. Evidence was restricted to this image and its original decompiled functions, retry-180-phase1 functions, assembly.txt, calls.csv, and function_ranges.csv. No runtime execution or owner observation was used. This note describes observed native behavior and limits; it does not prescribe replacement behavior, capture procedure, global quiescence, or a universal lock order.

The principal routine is RVA 0x2d9480. Its machine-level argument positions are World address in RCX, destination address in RDX, and target actor address in R8. RAX returns the same destination address. The destination is caller-supplied storage for three consecutive 64-bit fields, totaling 0x18 bytes. This is an addressable result object rather than a scalar text pointer. The entry saves all three incoming addresses before inspecting the actor. There is no null test for the World, actor, or destination, and no validation of their lifetime. The routine constructs its result without first releasing any preexisting allocation described by the destination. Native callers supply temporary destination storage. No permission to overwrite an independently live owning result follows from this interface.

The result fields at offsets 0, 8, and 0x10 describe the beginning of a contiguous string sequence, its logical end, and its allocation end. Each element occupies 0x20 bytes. Within an element, offsets 0 through 0xf are the inline byte buffer or a heap-pointer representation; offset 0x10 holds the 64-bit character count, and offset 0x18 holds the 64-bit capacity. Capacity at most 15 selects inline bytes; larger capacity selects the pointer stored at offset 0. The original append routine at RVA 0xa2030 advances the logical end by 0x20 and copies a string into a newly constructed element. Consequently temporary source strings can be destroyed after append without invalidating the appended string. The numeric-token append route at RVA 0x83a50 also forms and disposes of a temporary string. These layout conclusions are supported jointly by the append and destruction routines, rather than by a decompiler type declaration.

The actor byte at offset 0x14c selects two direct special cases, 0x9b and 0x84. The 0x9b case additionally reads the actor reached through World+0x448, specifically its bytes at offsets 0x14c and 0x14d. The 0x84 case reads the 32-bit floating value at World+0xc and the signed 32-bit value at offset 0xaac of the actor reached through World+0x448. Other actor categories read signed 64-bit coordinate values at actor+0x1b8 and actor+0x1c0 and derive integer coordinates before entering RVA 0x2ada20. Thus the actor argument is a native object address, not an isolated category or identifier value. World+0x448 is a pointer field; the lock locations discussed below have a different, inline relationship to the World address.

For the ordinary path, RVA 0x2d9480 obtains an eight-byte coordinate result through RVA 0x2ada20, builds a temporary generation context through RVA 0x115df0, calls RVA 0x12a6f0 with that context, temporary output storage, and the original actor, transfers the three output fields to the caller destination, and destroys the context through RVA 0x82450. The context constructor records a borrowed World address at context offset 0 and two 32-bit coordinates at offsets 8 and 0xc, while constructing owning temporary containers. The context is not the output object. The transfer of the three result fields occurs before temporary cleanup; the source result fields are cleared before RVA 0x81790 is called at callsite 0x2d9b26. That particular destruction call therefore receives an empty moved-from result, and does not free the result now owned by the caller. The direct special cases likewise leave their result allocations owned by the caller.

The ordinary path has substantially more input reach than the direct special cases. RVA 0x12a6f0 reads the actor identifier at offset 8 and the World integer at offset 8 for its decision state, actor fields including offsets 0x60, 0x64, 0x80, 0x128, 0x14c, 0x19c, the position at 0x10 and 0x18, and the coordinates at 0x1b8 and 0x1c0. It also follows World+0x448 to player progression, inventory, and equipment-related data. For example, the reached inventory query at RVA 0x5e780 walks the player containers described at offsets 0x9f0 and 0x9f8 and their nested elements. This is a supported example of transitive input reach, not a complete actor or World layout and not a complete list of every consulted allocation.

Output disposal is bounded by RVA 0x81790, with the owning three-field result address in RCX. If the first field is nonzero, it calls RVA 0x70000 over the logical element range and RVA 0x91000 for the outer allocation, then clears all three fields. RVA 0x70000 destroys 0x20-byte string elements and frees an element's heap storage when capacity exceeds 15. RVA 0x91000 frees the outer sequence allocation using its capacity in elements. Both routines include native allocation-metadata checks for large allocations; malformed ownership metadata may terminate through the runtime invalid-parameter path. These routines contain no observed World critical-section acquisition and receive no World or actor argument. This bounds the inspected disposal path to owned strings and storage; it is not a general statement about all allocator-internal synchronization. Native callers destroy the actual returned sequence at callsites 0x98ec8 and 0xa9882 after consuming it.

The lock helpers were identified directly from their original instructions and imported Windows calls. RVA 0x2abb70 adds 0x3c8 to its incoming World address and enters the critical section at that address; RVA 0x2b9890 leaves that same address. RVA 0x2abb80 and RVA 0x2b98a0 perform the corresponding operations at World+0x3f0. Neither helper loads a pointer from the offset before calling the Windows operation. These are two distinct inline critical-section locations, 0x28 bytes apart. An offset alone is not sufficient to identify either section on some other object.

Two direct generation callsites are present in the original direct-call evidence. RVA 0xa5a50 calls generation at 0xa97b9 while iterating identifiers from a World-owned container at World+0x170, resolving each actor through RVA 0xe720 and skipping absent actors. This enclosing routine enters World+0x3c8 through RVA 0x2abb70 at 0xa6464 and leaves through RVA 0x2b9890 at 0xadb23. Its generation, result consumption, follow-up call to RVA 0x98040, and result destruction occur within that enclosing interval on the inspected normal path.

The second direct generation caller is RVA 0x98180, at callsite 0x98e07. That routine itself contains no observed entry into either World critical section. The known native caller RVA 0x8ae50 invokes it at 0x8df69, and RVA 0xa5a50 invokes RVA 0x8ae50 at 0xa9b2c, inside the same enclosing World+0x3c8 interval. Thus this specific native route inherits +0x3c8 protection from its ancestor. This does not establish that arbitrary direct invocation of RVA 0x98180 or RVA 0x2d9480 acquires protection. RVA 0x2d9480 itself contains no direct call to the four World lock helpers or the Windows critical-section operations. Neither of the two established generation routes is shown to enter World+0x3f0 for the generation interval.

Generation is not established as free of reached synchronization or non-output side effects. One conditional ordinary-generation route calls RVA 0x119660 from RVA 0x12a6f0 at 0x12c44b. This context lookup can initialize a process static fallback object at image RVA 0x5519d0, governed by a guard at RVA 0x551a70. The reached native runtime helpers at RVAs 0x392dc8 and 0x392d68 enter the runtime critical section at image RVA 0x5535c8 and update initialization and thread-local bookkeeping. The wait helper at RVA 0x392e8c has a path that releases and reacquires that runtime section. When reached through the established caller ancestry, these are runtime-lock operations nested within the caller's still-held World+0x3c8 interval. They are conditional, and they concern a runtime section distinct from World+0x3f0.

Another ordinary-generation branch calls imported srand at RVA 0x12e96d, then reaches one of RVAs 0x13ffc0, 0x142000, or 0x142190, each of which uses imported rand. This establishes a runtime random-state side effect beyond writing the returned token sequence. The branch through RVA 0x142000 can also initialize static container state and register cleanup with atexit, using the same class of runtime initialization helpers. The precise CRT random-state sharing scope, every runtime-internal lock, and the scheduling effects of those operations were not established from the supplied native image alone. These observations preclude describing all ordinary generation as merely reading World fields and allocating its final output.

Separately inspected native World maintenance supplies concrete examples involving both inline sections, without proving that those routines are descendants of conversation generation. RVA 0x2ae0c0 enters +0x3f0 at 0x2ae321, enters +0x3c8 at 0x2ae32e, modifies the World container rooted at +0x460, then releases +0x3c8 and +0x3f0. RVA 0x2d2410 initially enters and leaves +0x3c8 for player-position reads, then enters +0x3f0 for a container traversal and conditionally enters +0x3c8 while still holding +0x3f0 for removal work. These are observed local acquisition sequences. They neither demonstrate a universal order nor establish a safe additional acquisition sequence for an unrelated caller already holding one of the sections.

The established protection is the particular native caller interval above. Its presence alone does not prove exclusive access to every World or player allocation, comprehensive lifetime protection for every reached pointer, absence of writers using a different section, or transitive lock-freedom. The bounded audit does not resolve every indirect target, exceptional cleanup route, allocator or CRT implementation detail, possible external entry, or complete mutation footprint of all descendants. No whole-game writer census, universal quiescence claim, or complete deadlock analysis is made. Unproved scope remains unproved even where a direct callee has no visible lock operation.
