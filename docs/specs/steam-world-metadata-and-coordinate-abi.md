# Original World metadata and coordinate arguments

This bounded contract supports the original AMD64 PE32+ image cubeworld.original.exe.unpacked.exe, 5,757,952 bytes, preferred base 0x140000000, SHA-256 7AF18CB28C8BF848F355287428C6390B2EA2A682CA466190F5EB9859C5D6F244. All routine addresses are RVAs. Evidence is restricted to the original image and original native function, assembly and call records. No game, probe or build was run. This is a layout and ABI contract, not a reproduction of generation or update algorithms.

## World metadata

The supplied generation seed is a four-byte field at World+0x220. Setup routine 0x2b5f20 receives this value as a 32-bit unsigned argument, stores it there and passes the same value to srand. It also creates other generation state. The four-byte value at World+0x244 is a distinct derived generation value: that setup routine assigns a rand result reduced modulo 100000, and generation consumers read it as a signed four-byte integer. Zone creation 0x2ae0c0 combines the +0x244 value with its two coordinate components before reseeding the CRT RNG. The primary seed and this derived value must not be conflated or represented as one eight-byte scalar.

World+0x70 is different again. Constructor 0x29a130 stores its eight-byte second argument there. The ordinary startup path supplies a separately constructed object returned by 0x172f60; it is not the 32-bit seed argument subsequently supplied to 0x2b5f20. In particular, an eight-byte load from World+0x70 is not evidence for an eight-byte World seed.

The day/counter is a four-byte field at World+0x08. Update 0x2e2e80 increments it as a signed 32-bit integer when the time accumulator crosses its native threshold. Packet receiver 0x3e450 case 8 compares and assigns it as a signed four-byte integer. The native code does not establish an unlimited mathematical day number or a signed-overflow recovery contract.

World+0x0c is a separate IEEE binary32 floating-point time accumulator. It is not the upper half of a 64-bit day value. Update 0x2e2e80 adds an elapsed-time-dependent amount, chooses a different rate when its examined actor condition holds, subtracts the native cycle threshold when advancing the counter, and can directly set a time constant in another mode. This establishes the accumulator/counter relationship without establishing a universal units or wall-clock interpretation for every caller.

Setup 0x2b5f20 has an established initialization branch that writes day 1 and time bits 0x4c095440 to World+0x08 and +0x0c respectively. Its seed assignment at +0x220 precedes its generation work. These are later setup facts, not direct stores by the outer World constructor. Constructor 0x29a130 directly establishes collection/state members and the +0x70 pointer; no direct outer-constructor stores to +0x08, +0x0c, +0x220 or +0x244 are established here. It is therefore not justified to treat a return from the outer constructor alone as proof that these four metadata fields have their later setup values. This audit does not provide a complete transitive initialization or persistent-load census.

The ordinary Game constructor 0x7ea80 calls 0x2b5f20 on its supplied World pointer. Hosted constructor 0xf17a0 calls it on its embedded World with seed 0x7b and a native name string. These are different owner paths: Game+0x08 contains a supplied World pointer, whereas the hosted World is inline at Game+0x6f0 on the examined Game path. A metadata observation must retain which World is being addressed.

An additional time-related field at World+0x440 is a four-byte float. Constructor 0x29a130 initializes it to zero, and 0x2e2e80 adds its elapsed-time argument to it separately from the +0x0c time-of-day accumulator. It must not be substituted for +0x0c. Its complete lifetime/reset meaning remains unproved.

The hosted send routine 0xf5520 reads the embedded World's day as four bytes and converts its +0x0c float time to a signed four-byte integer for packet type 8. Receiver 0x3e450 reads two four-byte integers, assigns the first to the receiving World's +0x08, and converts the second numerically to float for +0x0c. This is not transmission of the original float bit pattern and does not preserve arbitrary fractional time values. A changed received day also reaches 0x2c34c0. Truncated-packet behavior is outside a valid-input contract.

Day update has additional effects. Routine 0x2e2e80 inspects actors, can modify a particular actor's health, updates +0x440, and on a day transition can invoke World routines and append a temporal notice. Seed setup and zone creation modify CRT RNG state. Merely identifying these scalar offsets does not make the native routines read-only metadata accessors.

## Zone constructor 0x2f9400

Under Windows x64 conventions, RCX is the caller-provided Zone destination, RDX is the associated World pointer, and R8 points to an eight-byte coordinate pair consisting of two adjacent four-byte components. RAX returns the destination base on normal completion. The coordinate argument is a pointer to data, not two coordinates passed in R8 and R9, a pointer to two eight-byte integers, or an array of doubles.

Constructor 0x2f9400 writes the World pointer at destination+0x08, copies the first four-byte component to destination+0x10, and copies the second to destination+0x14. The native coordinate caller 0x2ae0c0 receives signed four-byte coordinate arguments, places the first at the lower address and the second four bytes later, and passes their address. Assembly at 0x2ae157 through 0x2ae16a establishes these stores and RCX/RDX/R8 preparation directly. Although the decompiler can display the temporary as one packed eight-byte value, the callee consumes two four-byte components in that order. A cardinal-axis naming convention beyond the first/second coordinate relationship is not required by this evidence.

The ordinary caller allocates 0x58518 bytes before constructing the Zone. The constructor initializes owning collections and an inline array of 0x1000 elements with a 0x58-byte element stride, beginning at destination+0x518. It requires writable object storage; the observed route does not require the destination to be pre-zeroed. It is construction, not assignment to an already live Zone: existing owning members would be overwritten by fresh construction. It copies the coordinate values rather than storing the input pair pointer in the initial coordinate members. The pair must remain readable during the call; no ownership transfer of it is established.

Constructor completion is not full zone generation. Caller 0x2ae0c0 separately invokes 0x2ff6f0 after construction, applies additional state, and publishes the resulting pointer to a World collection. Destructor 0x2f9940 handles the constructed Zone's owned members. Deleting wrapper 0x2fa3b0 invokes that destructor and conditionally frees the top-level allocation when its deletion flag's low bit is set. Allocation failure, partial-construction exception cleanup and subsequent generation failure are not represented here as a dependable nullable result protocol.

## Region-role constructor 0x115df0

This entry likewise receives destination in RCX, World pointer in RDX and coordinate-pair pointer in R8. The input contains two adjacent signed four-byte integers in first/second order. Its initial stores put World at destination+0x00, the first coordinate at +0x08 and the second at +0x0c. It performs signed arithmetic on these components and derives surrounding spatial queries from them. It is not an ABI for an eight-byte component pair even when a caller displays its input in one packed temporary.

Direct callers 0x2b4260, 0x2bb290 and 0x2e1750 supply temporary stack destination storage and pass the address of the local Creature's adjacent +0x150 and +0x154 values. For example, assembly at 0x2b4296 through 0x2b42a5 forms that address in R8 and prepares RDX and RCX independently. Other callers, including 0x2d4290, construct an explicit local coordinate pair. This proves pointer-to-pair consumption without assuming a layout from caller variable names.

On normal completion RAX identifies the constructed destination. The examined ordinary callers provide a 0xb0-byte stack region, immediately use the returned object for role/query operations and destroy it through 0x82450. The constructor initializes multiple owning collections and scalar members, with established initialization through destination+0xa7; it does not require a zero-filled destination. The caller's 0xb0 reservation is not a proof that every byte is initialized or a universal heap-allocation size for this object.

This is construction into fresh destination storage, not assignment. It writes the World pointer and coordinate values and constructs new owning members. Routine 0x82450 destroys the resulting owned collections and buffers without freeing the caller's destination itself or the supplied World. The caller retains destination storage responsibility. The coordinate pair is borrowed during construction; the initial destination coordinate fields contain value copies. Arbitrary reuse of a still-live destination, copying the constructed object as raw bytes, or destroying a partially constructed object after an exception is outside the established contract.

The constructor performs spatial World queries and builds nontrivial result collections; it is not merely an eight-byte coordinate copy. Direct calls include 0x2b9080, 0x2b99d0, 0x2ada20 and 0x2aa270. No direct rand/srand call was identified in this constructor's examined call records, but that is not a proof that its transitive queries are free of RNG use, allocation, cache changes, I/O or locking. A complete role taxonomy and the generation algorithm are outside scope.

## Protection and lifetime limits

The scalar fields belong to the particular live World object. Their offsets do not establish that World destruction, setup, day update, packet assignment or a multi-field observation is excluded by any one universal lock. The examined frame and hosted update routes hold their respective World+0x3c8 sections over portions of native update/packet/query work, but these are caller facts rather than a complete writer/lifetime census.

Zone creator 0x2ae0c0 performs construction and generation before its explicit publication section. It then enters World+0x3f0 and nests World+0x3c8 while storing the resulting pointer, releasing the latter first. This established nesting does not prove that all generation occurred under those sections or prescribe an order for other callers. Neither coordinate constructor supplies a general owner-lifetime guard. Destroying the destination's owned state and releasing the associated World are separate lifetime events.
