# Steam personal ground-item pickup history

Original evidence is the x64 Steam image `cubeworld.original.exe.unpacked.exe`, SHA-256 `7AF18CB28C8BF848F355287428C6390B2EA2A682CA466190F5EB9859C5D6F244`, and its instruction and routine exports. Addresses are RVAs relative to `0x140000000`.

## Selection and authoritative pickup

The input scan at `0x8AE50` selects a ground slot by three integers: zone X, zone Y and zero-based slot index. `0x2B8FD0` resolves that address against a resident zone's 224-byte ground entries. The pickup request carries those three integers and the selected item description. The slot index identifies a particular ground entry even when multiple entries share world X and Y. It is not a height. Input checks the usual reservation and carrying conditions. Unflagged categories `0x0C` and `0x0E` have an automatic pickup path when their settling field is zero. Bit `0x02` in the ground entry's flags at `+0xC4` excludes that automatic path. For an automatic request, the pending-action check compares type 7, zone X, zone Y, slot index and the expected item description. This suppresses a matching action already queued for that actor. The input scan and manual enqueue do not insert a personal pickup position.

The authoritative type-7 action at `0x2C3710` resolves the requested slot, checks its bounds, the three-dimensional distance to the actor (squared distance at most 16 in block units) and the expected item description. A successful action queues a receipt for that actor with the actual ground item's quantity, original three signed 64-bit position components (`+0xA0`, `+0xA8`, `+0xB0`) and flags. The comparison at `0x2C3EF8` comes after the receipt is queued. With bit `0x02` clear, it marks the zone's ground collection changed and replaces the slot with an empty entry (`0x2C3FB6`, `0x837E0`). A second action for the old item then fails the item match. With bit `0x02` set, the ground entry stays available for another action. This branch performs no character-history lookup or insertion.

## Local receipt and duplicate identity

Receipt processing at `0xAA620` resolves the recipient and derives the character-specific item. Only the local recipient executes the history and credit path. For bit `0x02`, three calls to `0x93870` at `0xAA671`, `0xAA683` and `0xAA695` convert the ground item's receipt X, Y and Z separately to signed block coordinates. Each block is 65,536 native position units wide. For representable block coordinates, the conversion rounds down on every axis, including negative fractions. An exact negative block boundary stays on that block.

The key is exactly three signed 32-bit integers, ordered X, then Y, then Z. Lookup `0x937D0` and its lower-bound search `0x764C0` compare components in that order. The first unequal component decides the signed ordering. A duplicate requires all three components to match. Item identity, quantity, ground slot index, zone key, day and the remaining fractional coordinates do not participate. All flagged item categories share this position set on the character's extended state at `+0x88`.

An existing triple jumps directly to the next receipt (`0xAA6EF`, `0xAADAE`), skipping local credit and the pickup message. A new triple is inserted at `0xAA71C` before item-specific credit and message handling. With bit `0x02` clear, the receipt bypasses this lookup and insertion and proceeds to those handlers. A receipt addressed to another actor skips the local history and credit, but can run the other-actor notification (`0xAAD68`, `0x9D6F0`). Thus each recipient can receive a shared flagged item once at the same position while its own entry is present. This describes stock action and receipt processing; other eligibility rules can still hide an item or prevent selection. The evidence does not establish scheduling order for simultaneous actions from different machines.

## What the player can see

The common eligibility test `0x2B8140` is called by the input scan at `0x8D4DE`, a ground display pass at `0xD88E5` and a ground visual-effect pass at `0xCE79F`. It rejects an empty category or zero quantity. With a local player, it also checks category-specific conditions and the reservation identifier. The generic flagged-item XYZ history at `+0x88` is not an input to this test. The shared flag alone consequently does not guarantee that a credited ground item disappears or loses its pickup prompt. A repeated action can reach the local receipt check and give no further credit.

Category `0x1E` has a separate, coarser history. Following a credited local receipt of that original ground category, `0xAA7EA` through `0xAA83B` insert a signed X/Y pair in the character collection at `+0xA8`, regardless of the shared flag. Each component comes from the ground position: first find the containing block, then the containing 16-block interval (`0x137E0`, floor in both steps). `0x2B8140` suppresses that category when the horizontal pair is present. Z plays no part in this display and selection check. Category `0x17` has a possession check and `0x18` its own eligibility check; neither substitutes for the shared receipt's XYZ test.

## Character save, reload and reset

The current character writer `0x149760` uses version 11 (`0x147750`). At `0x149F47` it obtains the personal XYZ count from extended-state `+0x90` and emits a four-byte little-endian count. Each entry occupies exactly 12 bytes: signed little-endian 32-bit X, then Y, then Z, with no gaps. Entries appear in ascending signed lexicographic order, independently of acquisition order. The preceding collection is the one at `+0x58`; a different counted collection of 12-byte entries at `+0x98` follows. The separate category-`0x1E` collection at `+0xA8` has its own four-byte count and eight-byte signed X/Y pairs in order. The XYZ history is part of the character data and carries no item or world identifier in its section.

The character reader `0x147800` prepares fresh extended state. For stored character versions greater than 9 it reads the XYZ count and 12 bytes per entry and inserts through `0x8FD0` (`0x1482BD`). A valid file with repeated triples resolves to one set entry; a subsequent write emits each distinct triple once in signed order. The adjacent collection at +0x98 has its own count at +0xA0 in memory. On disk it is a four-byte count followed by triples of three signed 32-bit components, 12 bytes per entry. Reader call 0x14836D uses the very same unique-key insertion as the personal XYZ collection. Signed ordering and equality therefore include the third component here as well. Each set has its own membership, so the same triple can appear once in each. These facts establish the adjacent collection's dimensions and ordering; its gameplay purpose is unresolved. The same version branch reads the separate X/Y collection. Older versions skip these history sections. Loading a valid current character restores the recorded triples exactly, without rounding the stored block coordinates again.

The daily reset `0x2C34C0` clears the local player's complete `+0x88` set at `0x2C3656` when there is a local player. The routine does not clear `+0xA8`. The authoritative clock rollover calls that reset at `0x2E3015`; a zero world event also calls it at `0x2DB70B`. Receipt of a changed day in a type-8 day/time update calls it before replacing the day (`0x3ED64`). There is no per-triple timer in the serialized history. Clearing the XYZ history permits a future receipt at that triple to pass its duplicate check. Separate inventory, reservation and category-specific conditions still apply. The reset of live character state and writing the character file are distinct operations.

## Examples

- Flagged ground positions `(-1, 131072, -65536)` and `(-65536, 131073, -1)` in native units both map to block `(-1, 2, -1)`. The first qualifying local receipt records one triple. The second yields no additional credit, even for a different flagged item in another slot. A one-entry XYZ section for that triple is `01 00 00 00 FF FF FF FF 02 00 00 00 FF FF FF FF`.
- At the same native X/Y, raising Z from `-1` to `0` yields two distinct XYZ keys, `(-1, 2, -1)` and `(-1, 2, 0)`. A non-`0x1E` flagged item can consequently yield both credits when otherwise eligible. For category `0x1E` both positions share coarse X/Y `(-1, 0)`, so the first credit can suppress the other item from ordinary selection and display.
- If two characters start with empty XYZ histories and both can select the same flagged slot, each character's own first receipt can credit it. For an ordinary slot, the first successful authoritative action clears the slot, independently of either character's XYZ history.
