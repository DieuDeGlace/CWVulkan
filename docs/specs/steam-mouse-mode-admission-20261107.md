# Original Steam polled mouse-mode admission and delivery

FINAL / STABLE / HELD. Independent source-side behavioral contract, 2026-11-07. This document is bounded to the original polling path, its movement handler and the direct pointer routines needed to explain admission. It does not change or replace another held contract.

The authoritative image is the x64 Steam executable represented by `decompiled cube world steam\binary\cubeworld.original.exe.unpacked.exe`, preferred image base 0x140000000, PE timestamp 0x5D93AB0D, image size 0x58A000, SHA-256 7AF18CB28C8BF848F355287428C6390B2EA2A682CA466190F5EB9859C5D6F244. The packed original and installed supported executable have SHA-256 A1EFBBD41EEB8DF08395C4D6511194D416CB70A14054B2A2000B9F5CDBCFA65B. Every routine and instruction address below is an RVA in that original image. Original decompilation and original disassembly are the evidence; disassembly resolves omitted arguments and the pointer-query return value. Separately authorized reconstruction research supplied discovery leads only. No reconstruction-only behavior is promoted to a Steam fact here.

The central distinction is between the interface ownership predicate at 0x1014F0, the polled mouse delivery at 0x13683E within 0x1355A0, and the subsequent movement handler at 0x97880. Interface ownership selects an absolute pointer sample; otherwise the caller selects relative mouse motion. Pointer picking, capture, focused-widget state and controller-device indication are separate states with different admission effects.

The ordinary polling order in 0x1355A0 is as follows.

1. Pending Windows messages are translated and dispatched before the ordinary polling phase. The active-input byte at image RVA 0x536CE8 first admits cursor preparation. When it is clear, this branch sleeps 16 milliseconds and does not perform the ordinary keyboard, mouse or controller polling sequence.
2. With that byte set, the caller obtains the client rectangle and OS cursor, converts the cursor to client coordinates, and performs mode-dependent cursor preparation described below. This preparation precedes the later foreground test and the binding-capture test.
3. The caller again requires the active-input byte to be set and the game window to equal the foreground window. Failure sleeps 16 milliseconds and bypasses ordinary keyboard, mouse and controller polling. The examined path does not deliver a substitute zero-motion mouse call.
4. Keyboard and mouse device-state requests occur before the binding-capture decision. Their returned status values are not an additional admission test in this path. The binding-capture predicate at 0x9AE50 tests whether the controls panel has a nonnegative binding-selection index. When capture is active, the caller processes binding selection instead of the ordinary held-control rebuild, mouse delivery and XInput poll. This diversion does not deliver an ordinary neutral mouse sample.
5. Outside binding capture, the caller rebuilds the 23 configured keyboard/mouse held controls. A pressed configured keyboard or mouse control clears the game object's controller-device indication at offset 0x1958. The caller then samples interface ownership again, chooses absolute or relative mouse coordinates, and unconditionally calls 0x97880 at instruction 0x13683E. There is no motion-is-nonzero test at this call site.
6. Only after the mouse call does the caller prepare the controller state, clear controller-specific held controls 21 and 22, and poll controller zero at instruction 0x136881. Current controller processing can subsequently set the controller-device indication and synthesize button callbacks. It cannot retroactively change which indication the earlier mouse handler observed.

The controller-device indication is therefore not a fresh result of the current XInput poll when mouse handling runs. It can retain an earlier value, subject to the preceding configured keyboard/mouse held-control phase. Mere relative mouse displacement does not itself clear it in that phase. The engine button mask used by dragging is also a distinct stored state: this contract does not equate a newly polled mouse button array with an immediate write of that mask. The bypasses above identify the absence of this particular polling and movement-delivery sequence; they do not establish that the rest of the game stops updating. The outer routine still reaches its later frame path.

Cursor preparation in 0x1355A0 has two different forms. In relative mode, either client-coordinate component must be more than 500 units from its corresponding client-center component before recentering is considered. Equality to 500 is insufficient. Recentring additionally requires the game to be the foreground window. The target is half the client rectangle's right and bottom extents, converted to screen coordinates for the OS cursor-position call. This path clears the cursor-transition byte at image RVA 0x551A8C. A relative-mode pass that does not recenter does not necessarily clear that byte; it is not rewritten into an exact mode snapshot every pass.

In interface-owned mode, a zero cursor-transition byte causes the caller to take the engine's stored current pointer, truncate its components to integers, convert that point from client to screen coordinates, and potentially place the OS cursor there. The actual comparison is between this converted screen point and the earlier OS cursor sample already converted to client coordinates. These coordinate spaces differ in the original; this contract preserves that fact. The caller then sets the transition byte to one whether or not it repositioned the cursor. This interface cursor preparation is inside the first active-input gate but before the later foreground gate. Consequently the examined interface-entry repositioning does not itself require foreground ownership, whereas relative recentering explicitly does. Binding capture also occurs later and does not suppress the earlier cursor preparation.

For movement delivery, an interface-owned sample comes from a new OS cursor query. If the coordinate-option global at image RVA 0x551BF0 is zero, the caller converts that sample to client coordinates; when it is nonzero, it retains the queried screen coordinates. The selected integer components are converted to floats. In relative mode, the selected values are the signed horizontal and vertical motion components from the polled mouse state, also converted to floats. Original instructions 0x1367EB through 0x13683E establish these alternatives and their common unconditional call. No result from cursor preparation is added to the relative motion here.

The interface ownership predicate at 0x1014F0 examines a fixed set of panel visibility and interface-mode states, including the map-open state, menu-related panels and chat activity. It is not a query for any arbitrary node beneath the pointer, and it does not test the root's visibility. Pointer location, capture and focused-widget ownership are not interchangeable with this predicate. The bounded contract does not claim a complete semantic naming audit of every panel tested by that predicate.

On entry to 0x97880, interface ownership is tested again. If owned, the handler truncates the supplied float coordinates to integers and calls the interface pointer routine at 0x101160, at instruction 0x978E3. That routine converts the integer pair back to floats and publishes it through 0x3418D0 at instruction 0x101195, then performs its additional interface processing. This is publication of an absolute position, not addition of a relative displacement.

After that interface processing, 0x97880 tests the controller-device indication. A nonzero indication returns immediately, after pointer publication but before its pointer-moved flag, map drag, customization turn and camera work. This early return belongs to the interface-owned entry branch. Relative-mode entry does not have this device-indication gate.

With the indication clear, the handler obtains displacement from the engine's stored current and previous pointer coordinates. Any nonzero component sets the game's pointer-moved byte at offset 0x1DB0. A stationary call does not clear that byte in this handler. The map and customization branches then use the stored pointer displacement and the engine's held button mask at offset 0x1A8.

Map dragging requires the game map-open byte and engine button one, the right mouse button, to be set. It has no pointer-under-map, fresh root-pick, captured-node or focused-widget test in this handler. Horizontal pointer displacement and negated vertical displacement are scaled by two raised to the current map-zoom integer. The displacement is rotated using the current camera yaw, converted to the map position's fixed-point units, and added to the desired map position. The map-changed byte at game offset 0x1E38 is set. The admitted branch sets that byte even when the displacement is zero. The current-yaw input is explicit in original instructions 0x97983 and 0x979B0; it is not the desired-yaw field changed later by camera motion.

Customization turning independently requires the customization panel's own node visibility to be nonzero and the same engine right-button state. It does not require that panel to be under the pointer, to have capture, or to be focused. Its model pitch decreases with vertical pointer displacement; its model yaw increases with horizontal pointer displacement. Both use the configured integer camera speed multiplied by 0.005. The examined branch does not apply the later camera-pitch clamp to these model angles.

Map dragging and customization turning are successive independent tests. Neither admitted operation returns or consumes the movement call. Both can run when their respective states are present, and execution can continue into the later camera test. A held right button by itself does not admit the interface-owned camera test; if the left button is also held and that later test succeeds, camera work can follow the right-button work.

For that later camera test, 0x97880 reads interface ownership again. Relative-camera mode admits camera motion directly, without testing an engine mouse button, pointer capture, root hit or focused widget. In interface-owned mode, camera motion instead requires engine button zero, the left mouse button, and a null result from 0x33F1E0. The query occurs at instruction 0x97B9C and its result is tested at 0x97BA1. No focused-widget getter is called in this movement handler.

The result of 0x33F1E0 is precise. If the engine's capture pointer at offset 0x168 is nonnull, it returns that captured node directly. It does not recheck that node's visibility or position. Without capture, it performs a fresh root pick through 0x333F60, using the root at engine offset 0x140 and the current published pointer at offsets 0x180 and 0x184. Original disassembly at 0x33F1E0 through 0x33F202 establishes the returned value despite incomplete decompiler return typing. It does not return the retained movement-hit pointer at engine offset 0x160, nor the focused-widget pointer at offset 0x170. The separate getter at 0x342090 returns the latter state and is not used for this camera admission.

The root pick's own admission at 0x333F60 first requires that root's stored visibility be nonzero and specified exclusion flags be clear, before it can traverse children. A hidden root therefore returns null without searching its children, even if a child's own visibility remains set. With no capture, that null result can satisfy this camera test when the left button is held. Capture bypasses the root pick entirely and supplies a nonnull result even when the root is hidden. A visible root is not automatically a nonnull hit: the picker still applies its native transforms, clipping, descendants, eligibility and hit rules. This contract does not replace those rules with an assumption that every visible GUI blocks camera motion.

After camera admission, the handler reads interface ownership yet again to choose its displacement. If owned at that point, it uses engine current-minus-previous pointer coordinates. Otherwise it uses the supplied movement values. For ordinary unchanged mode this means an interface drag uses pointer displacement, while relative mode uses the polled relative motion. The repeated reads are real; the caller's mode choice and all later handler choices are not one immutable snapshot. Pointer publication can dispatch interface callbacks before the later choices, so the contract does not assume those callbacks cannot change relevant state.

Camera vertical motion uses configured integer speed multiplied by 0.005. It adds to desired pitch when the inversion setting is zero and subtracts when that setting is nonzero. Desired pitch is then bounded to 0 through 180 degrees. Horizontal motion decreases desired yaw using the same speed factor. These are desired camera-angle outputs, distinct from the customization model angles and desired map position. Player-facing or aim-target publication is not established by this handler.

Stationary delivery has observable work. The engine publisher at 0x3418D0 copies current pointer coordinates into the previous-coordinate fields before storing the supplied absolute coordinates. It resolves capture or a fresh root hit, compares the old and new associated handlers for applicable leave/enter dispatch, dispatches the target's applicable movement callbacks, stores the movement-hit pointer, and performs its admitted root/tree pointer traversal. It has no nonzero-displacement admission check. A stationary interface call can therefore publish state and dispatch callbacks, even though the game pointer-moved byte is not newly set for zero displacement. It can also reach the admitted zero-displacement map branch described above. An admitted relative zero-motion camera call still executes the pitch bounds, which can correct an already out-of-range desired pitch. Omitting the call and delivering a zero sample are different operations in this original path.

The bounded unresolved facts are the complete producer and initialization sets for the active-input byte, cursor-transition byte, coordinate-option global, controller-device indication, engine button mask, capture pointer and focused widget; the complete semantic naming of the ownership predicate's panel set; all alternative mouse/message and pointer-publication callers; and every callback's possible state changes. The inspected path does not add recovery gates for OS cursor or device-state request failures, but this does not prove valid fresh samples on failure. This is not a complete window-message, controller, UI-tree or root-picking audit. Those omissions do not weaken the direct admission and ordering facts above.
