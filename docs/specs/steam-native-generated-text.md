# Steam native generated text

This bounded native-only contract supports cubeworld.original.exe.unpacked.exe, 5,757,952 bytes, SHA-256 7AF18CB28C8BF848F355287428C6390B2EA2A682CA466190F5EB9859C5D6F244, preferred image base 0x140000000. All addresses below are RVAs. Evidence was restricted to the original binary, original functions and retry-180-phase1 functions, assembly.txt, calls.csv, and function_ranges.csv after reading the standalone native-author rules. No other project prose, SDK, replacement implementation, tests, probes, owner outputs, or runtime execution supplied facts. This is an ABI, ownership, and bounded behavior note; complete generated vocabulary and complete transitive synchronization are outside its scope.

RVA 0x611d0 uses Windows x64 integer argument positions with the caller-provided destination address in RCX, a 32-bit generation value in EDX, and a 32-bit category selector in R8D. The entry preserves the destination address, consumes the generation value at 32-bit width, and sign-extends the selector. Normal return places the original destination address in RAX. The destination is a native wide-string object, not a returned character-buffer address. The native caller at 0xab9ee supplies a temporary destination and selector -1; selector values outside explicit cases have a normal fallback selection route. That observation does not establish any complete semantic taxonomy for the selectors.

RVA 0x1628b0 has a different argument arrangement: RCX is a text-resource owner address, RDX is the caller-provided destination address, and R8 is the address of a native item-value record. Normal return places the original destination address in RAX. No fourth incoming argument is established as part of this entry's public calling contract. The routine immediately copies and normalizes the input value through RVA 0x1092b0. The underlying value-copy routine at RVA 0x35400 copies meaningful fields through input byte offset 0x9d, including a byte category, several 32-bit fields, and a nested fixed-size byte region. This establishes a native structured input whose referenced bytes must be readable; it does not establish that a category byte or numeric identifier alone can replace that record. The entire item layout, padding contents, and validity constraints are not specified here. Null or malformed owner, destination, and item addresses have no established normal failure handling.

Both entries produce the same 0x20-byte owning wide-string representation. The first 0x10 bytes are a union-like storage area. When the unsigned 64-bit capacity at offset 0x18 is less than 8, characters reside in that area; it holds eight 16-bit units, including room for the terminating zero. Capacity of 8 or greater selects a heap-buffer address stored in the first eight bytes. The unsigned 64-bit length at offset 0x10 counts 16-bit character units excluding the terminator. Capacity likewise counts character units excluding the terminator, rather than bytes. At the logical end there is a two-byte zero. Only the relevant representation fields and character range are established; unused union bytes and spare heap capacity have no defined text meaning in this note.

This is the native Windows wide-character representation, with two-byte code units and little-endian storage in the supported image. The originals use wide literals, two-byte terminator stores, and copy sizes twice their character counts. These results are not native narrow-byte strings or UTF-8 buffers. UTF-16 code-unit interpretation is appropriate for this Windows representation; a guarantee that every possible result is well-formed Unicode, contains no embedded zero, or uses a particular normalization or display-character counting convention was not established. The stored length, rather than a byte count or a Unicode scalar count, is the native string length.

The destination is storage supplied by the caller, while the string construction is performed by the called routine or its reached construction helpers. For RVA 0x611d0, RVA 0x4cc10 initializes destination length to zero, capacity to 7, and its first wide unit to zero before reserving and concatenating the selected components. RVA 0x1628b0 uses construction routes including RVAs 0x40430, 0x41d80, and 0x16a790; the latter extracts its assembled stream through RVAs 0x415a0 and 0x414a0. The inspected routes establish destination state themselves. Native callers provide stack temporaries without a separate required destination-constructor call immediately preceding these entries.

These operations do not establish assignment semantics for a previously live owning string. For example, RVA 0x4cc10 overwrites the destination's length and capacity before construction and does not first free an old destination allocation. Likewise, the other reached construction helpers initialize the destination representation before copying or transferring their newly created result. Fresh destination storage, an already-disposed string object, and an existing live owning string are therefore different cases. No ownership-preserving overwrite of an existing live result is proved. If an exception occurs before successful output construction, these entries do not provide an established guarantee that the destination already contains a valid empty string.

On successful return, the output owns its character storage. RVA 0x611d0 concatenates copies of selected static wide strings into the destination; it does not return the address of a static name-table entry. RVA 0x1628b0 constructs copies or transfers ownership from its temporary strings into the caller's result. The move helper at RVA 0x3bf00 copies inline characters or transfers a heap pointer, then resets the source to an empty inline string. Consequently cleanup of the internal source temporary does not free the returned destination's characters. The returned characters remain available while the result object and its owned allocation remain intact; mutation, movement, and destruction can invalidate a previously obtained character address. A shallow copy of the 0x20 bytes is not shown to create another independent heap allocation.

The actual callable wide-string cleanup entry is RVA 0x15c9a0. Its observed Windows x64 interface takes the string-object address in RCX and has no meaningful return value. It reads capacity at object+0x18. For heap representation it obtains the buffer address from object+0 and calls wide-buffer deallocator RVA 0x33b10 with the object address in RCX, the heap-buffer address in RDX, and capacity plus one in R8. It then sets capacity to 7, length to zero, and the first inline wide unit to zero. It does not release the caller's 0x20-byte object storage. It does not require the item or text-resource owner address.

RVA 0x33b10 frees the supplied wide allocation, interpreting its R8 count in two-byte units including terminator space. It contains separate handling when that byte size reaches 0x1000, validating the original aligned allocation metadata before freeing the underlying allocation. Malformed capacity, pointer, alignment, or metadata can reach the runtime invalid-parameter termination path. It is a lower-level deallocator whose native caller supplies the matching buffer and allocation count; it is not interchangeable with object cleanup or disposal of an inline character address. Original caller examples include destruction through RVA 0x15c9a0 at 0xacab2 after the result from 0xaca95 has been consumed, and conditional direct calls to RVA 0x33b10 in RVA 0x9d6f0 and RVA 0xb7b90. Those callers test capacity before deallocating.

For the resource owner passed to RVA 0x1628b0, the ordinary caller base is designated Game here solely to describe the observed native object relationship. At callsites 0x99abc, 0x9dbbe, 0xb7d46, and 0xaca95, the original instructions form the address Game+0x50 directly for RCX. There is no pointer load from Game+0x50 in that argument preparation. Constructor RVA 0x7ea80 separately calls RVA 0x1510f0 on that same inline Game+0x50 address. The owner is therefore an inline initialized subobject of these ordinary caller objects. This evidence establishes the path without assuming an SDK type or recovered member name.

The reached owner consumers further establish that this address is a populated resource object, rather than an uninitialized placeholder. RVA 0x16af30 follows a table pointer at owner+0x58 to obtain item-category text keys; RVA 0x16c750 searches the structure at owner+0x98 for keyed text resources; RVA 0x164760 uses a table pointer at owner+8 on a special naming route. The formatter also constructs temporary substitution maps and wide streams and can recurse through RVA 0x1628b0 for a normalized formula item. These examples identify actual resource dependencies. They do not specify the complete owner layout, constructor internals, resource loading state, or lifetime of all entries.

RVA 0x1628b0 returns text through several normal routes. It can prepend literal wide text for special categories, resolve and substitute keyed owner resources, and incorporate a generated name from RVA 0x611d0. One missing-resource route constructs the wide literal "unknown" and returns the destination normally; a reached lookup helper can also construct an empty string for an absent key. Therefore RAX equal to the destination is not an independent success indicator for resource resolution. Neither entry has an established Boolean, error-code, or nullable-character-pointer return contract. No universal nonempty-result guarantee follows.

The original string helpers can throw or terminate rather than convert all problems into fallback text. Reached routines RVAs 0x349d0 and 0x3d4f0 contain length-error paths, and allocator RVA 0xce180 reaches allocation-failure handling or invalid-parameter termination. Some helper paths have runtime-specific cleanup and security-cookie checks. This bounded audit does not certify exception guarantees, destination state after unwinding, or recovery from arbitrary invalid native inputs. Normal successful return and exceptional or terminating execution must remain distinct.

RVA 0x611d0 selects its components by arithmetic using its two numeric inputs and static wide-string tables. Its inspected body does not call imported rand or srand. It does perform conditional initialization of numerous static tables, registers their cleanup with atexit, and calls runtime initialization helpers RVAs 0x392dc8 and 0x392d68. Those helpers enter the runtime critical section at image RVA 0x5535c8 and update guard and thread-local initialization bookkeeping. Consequently generated output selection does not imply an absence of process or thread initialization side effects. These first-use effects can occur before destination construction.

RVA 0x1628b0 likewise has no direct imported rand or srand call in its inspected body. Its generation-related route can call RVA 0x611d0, for example at callsite 0x162efa, thereby reaching those conditional static initialization effects. Reached parser RVA 0x167c80 also selects resource alternatives using an explicit local numeric state. Temporary allocation, substitution, stream construction, and cleanup are observed effects. No claim that the complete descendant set is read-only, free of runtime synchronization, or unaffected by resource state is made, and precise RNG or locking behavior inside every external runtime component remains unresolved.

Neither text entry directly acquires the World critical-section helpers in its inspected body. There is nonetheless concrete caller-held protection on specific routes. RVA 0xa5a50 enters the inline critical section at the World address obtained from Game+8, offset +0x3c8, through RVA 0x2abb70 at callsite 0xa6464, and releases it through RVA 0x2b9890 at 0xadb23. Its direct name call at 0xab9ee and item-text call at 0xaca95 lie within that normal-path interval, including their shown use and cleanup. The route from this caller through RVA 0x8ae50 at 0xa9b2c to RVA 0x98180 at 0x8df69 likewise inherits that interval for the item-text calls in RVA 0x98180. The two helpers' original instructions establish an inline World+0x3c8 address passed to the Windows critical-section operations.

These are established native caller examples, not a required or sufficient universal protection scheme for text generation. Other inspected direct callers, such as RVAs 0x9d6f0 and 0xb7b90, do not themselves show acquisition of that World section, and their full ancestor protection was not established. A World section held by a caller does not by itself prove synchronization of the Game's text-resource owner, all resource allocations, or every runtime component. The complete writer set, valid publication interval, owner shutdown behavior, lock order, and all exceptional cleanup paths remain outside this bounded contract. No replacement implementation, capture policy, or universal quiescence requirement is prescribed.
