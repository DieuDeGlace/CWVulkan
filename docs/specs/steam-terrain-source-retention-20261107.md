Ordinary Steam source-terrain retention is not a single render-radius rule. The client World has a loaded-zone map, an independent missing-zone loader, and a mesh worker that performs bounded retirement before each mesh batch. A second World embedded in the host object uses a union of qualifying entity-centred source windows and a different retirement routine. Retaining an existing source zone does not by itself request generation, prefetch its neighbours or admit it to rendering.

The supported image is original x64 Steam binary/cubeworld.original.exe.unpacked.exe, preferred base 0x140000000, PE timestamp 0x5D93AB0D, SHA256 7AF18CB28C8BF848F355287428C6390B2EA2A682CA466190F5EB9859C5D6F244. Its hash was checked for this audit. Evidence is individually filename-selected original decompiled/functions files, the original successful retry-180-phase1/functions/1400a5a50.c output, address-scoped original decompiled/assembly.txt and directly inspected image constants/vtable entries. All native addresses below are RVAs; object offsets are byte offsets.

The ordinary startup at 0x1355A0 allocates a World through constructor 0x29A130, passes it to renderer construction 0xC3150 and to Game construction 0x7EA80, and retains that World at Game+0x8. Renderer base construction 0xCBD10 retains the same World at renderer+0x8. Each World contains its own coordinate-keyed loaded source-zone map at +0x460, with its list sentinel at +0x468 and count at +0x470. Zone constructor 0x2F9400 stores its owning World pointer at zone+0x8 and signed 32-bit zone X/Y at +0x10/+0x14. These resident source-zone objects are distinct from the active/prepared mesh-group lists contained within each zone.

Game construction also calls host constructor 0xF17A0 at 0x7EB36 for the object at Game+0x6E8. That constructor separately calls 0x29A130 for its embedded World at host+0x8, hence Game+0x6F0. This has a separate loaded-zone map and separate source-zone objects. The host worker is 0xF2340, reached through thread wrapper 0xF3220. The client mesh and source-loader bodies are 0x842D0 and 0x84F70, reached through wrappers 0x890C0 and 0x89160. Coexistence of these two Worlds does not establish shared zone ownership for equal coordinate keys or require that the host map be populated in every session.

The separate WorldMap object constructed by 0x2EAA00 stores the client World pointer at its +0x8; this does not turn the WorldMap's own caches into the loaded full-terrain map at World+0x460. Map-image/tile-cache retention is not audited here. A further coordinate-keyed state map at World+0x10 can retain selected zone state after a full source-zone object is removed: retirement helper 0x2D3E20 copies selected flagged data, collections and the zone+0x490 value into that map, and generation routine 0x2AE0C0 can consult it when the byte at World+0x358 is zero. Persistence of such a record is not continued residency of the full source zone.

For the ordinary client policy, let V denote the current signed 32-bit setting at Game+0x1B9C. The mesh/render zone radius is obtained by multiplying V by 30, dividing by 100 with signed truncation toward zero, and using a minimum result of 3. This contract calls that result the mesh radius. The described geometric regions assume ordinary non-overflowing values; the native integer products and coordinate arithmetic are not accompanied here by an invented overflow-safety guarantee.

At the beginning of each unpaused mesh-worker cycle, 0x842D0 samples its player-related centre from the object at client World+0x448. Its normal position components at +0x10/+0x18 are signed 64-bit fixed-point values with 65536 units per block; the mesh worker floors them to whole blocks and then floors division by 64 to zones. If the object's state byte at +0x68 is 0x9C, the mesh-candidate centre instead uses signed 32-bit block coordinates at +0x1B0/+0x1B4, floored to zones. This centre substitution is local to that path.

The worker then invokes source-zone retirement routine 0x2D2410 eight times at the loop containing call site 0x8456B. Each call receives one more than the mesh radius. Each call independently samples the ordinary position at World+0x448 under World+0x3C8, with floor conversion to the current zone. The retirement routine does not use the 0x9C destination substitution. Consequently, mesh/source demand around a destination and retirement around the ordinary position are independently proved branches; their centres are not assumed equal. Nor are the eight retirement calls a single frozen-position transaction.

For a positive input radius to 0x2D2410, non-null loaded zones at or inside the inclusive circular zone distance remain ineligible for this removal call. Only a zone strictly beyond that radius can be chosen. The routine starts its comparison threshold at the radius squared, computes signed 32-bit zone-coordinate differences, then compares squared distances as doubles. If either absolute coordinate difference exceeds twice the input radius, its comparison distance is replaced with four times the input radius squared. The selected map entry changes only on a strictly larger comparison value, so ties preserve the earlier selected entry in the current map traversal. This is the proved selection rule, not a claim that every extreme-distance zone is ranked by its exact Euclidean distance.

One call removes at most one selected zone. Therefore the eight calls remove at most eight zones in a mesh-worker cycle and need not clear every now-outside zone immediately. The routine does not condition source retention on camera visibility, a mesh's active-group count, mesh cost, dirty state or a missing-neighbour request. Having active or empty geometry does not change this inspected distance-based source removal predicate. Conversely, being outside the radius is removal eligibility, not a guarantee of removal before some fixed elapsed time.

The map traversal/removal uses World+0x3F0. For a selected entry, it acquires World+0x3C8 while still holding +0x3F0, calls 0x2D3E20 at 0x2D25FA, erases the source-map entry at 0x2D260E, then releases both guards. The zone's deleting virtual is invoked after those releases. The concrete zone vtable at image RVA 0x4738C0 resolves that slot to 0x2FA3B0, which calls zone destructor 0x2F9940 and frees the object when its deletion flag includes bit 0. This establishes actual source-object retirement rather than merely omitting a draw.

Client generation demand is collected separately by 0x84F70. Its block-space radius is obtained from V multiplied by 1920 and divided by 100 with signed truncation toward zero, with a minimum of 64 blocks. The image value at 0x432E84 is 64, selected when the computed value is at most 64. This is a block radius, not an additional fixed number of source-zone rings.

The loader normally converts the signed 64-bit player position components to whole blocks by truncation toward zero. When the state byte is 0x9C, it instead uses the signed 32-bit +0x1B0/+0x1B4 block destination. Its zone bounds are the floor-by-64 quotients of the centre minus the block radius and centre plus the block radius, inclusive on each axis. A missing/non-null distinction is then made in client World+0x460 for each coordinate in that rectangle. Only an absent entry or an entry with a null zone pointer can become a generation candidate.

A second loader admission test uses the zone containing the sampled block centre. It divides the block radius by 64 with integer truncation and then adds one; the sum of squared zone offsets must be at most the square of that result. Thus the ordinary missing-zone admission region is the intersection of the inclusive block-window-derived zone rectangle and this inclusive zone-space circle. The outer loop increases zone X and the inner loop increases zone Y. Already non-null source zones do not enter this missing-zone batch merely because the loader visits their keys.

The loader assigns candidate distance keys, orders its candidate vector, limits a nonempty batch to at most four entries at 0x855B5, and calls batch routine 0x7D5C0 at 0x855D7. The complete distance-priority/tie algorithm is not re-specified here. With no missing candidates it sleeps 5 milliseconds. Its loop also contains a zero-duration yield. The four selected source zones are a batch limit, not a statement that exactly four threads execute or that the entire demand region becomes resident at once.

Routine 0x7D5C0 directly calls 0x2AE0C0 for a single selected entry. Its multi-entry path reaches 0x76DA0, whose structured task collection waits at 0x77073; the reached generation chore 0x858E0 also joins its nested work at 0x85CC6. On ordinary completion, the source-loader loop does not rebuild another candidate batch until this call returns. This is a source-generation completion boundary. It is not a frame/render barrier or a proved global exclusion against every other World caller.

At entry, 0x2AE0C0 looks up the requested coordinate and returns an already non-null zone immediately. That hit is before the routine's random seeding, allocation and generation path. A miss instead reaches source-zone allocation/construction, 0x2FF6F0 generation and optional restoration from retained zone state. It finally acquires World+0x3F0 followed by +0x3C8 to install the resulting pointer in the loaded map. The early lookup alone does not prove an in-flight reservation, duplicate-work prevention or atomic ensure operation against untraced concurrent callers.

These rules directly distinguish retention from prefetch. As a finite arithmetic example, take V equal to 100 and an ordinary player centre at block coordinates 0,0. The mesh radius is 30, so a loaded zone at offset 31,0 is on the retained radius-31 boundary and is not eligible for the inspected distance removal. The loader's block radius is 1920, whose inclusive rectangle covers zone coordinates minus 30 through plus 30. That absent zone at 31,0 is outside this generation rectangle. This example derives the native boundary rules; it is not a runtime capture or a proposed engine cache policy.

Meshing has a separate loaded-neighbour requirement. Within the mesh-radius square around its sampled centre, 0x842D0 collects existing non-null source zones and applies its mesh cost/dirty/batch gates. Before selecting a candidate it calls 0xCE3E0 at 0x84A72. That routine requires all nine non-null source zones in the candidate's 3 by 3 neighbourhood, covering offsets minus 1 through plus 1 on each axis, under World+0x3F0. It returns false on the first absent/null neighbour. It does not call generation or enlarge the source-loader region. A loaded centre can therefore be retained yet fail mesh admission because a required neighbour is missing.

The mesher 0xE9530 independently obtains its raw 3 by 3 neighbourhood through 0xCBFC0 while holding +0x3F0 at 0xE962E through 0xE968E. This snapshot is a set of raw pointers, not demonstrated reference-counted ownership or a demand token. In the ordinary mesh worker, retirement is before candidate collection and the mesh call at 0x84C19. The multi-entry mesh task path waits at 0x773F3 before the worker's reached preparation/publication phases. Only after those phases and local cleanup can that same worker begin its next cycle's eight retirement calls. No next-cycle retirement overlaps its own still-running ordinary mesh batch. Alternate callers and other destruction paths are not granted that guarantee by inference.

Rendering and preparation make another distinct demand read. Game update 0xA5A50 supplies Game+0x1DC0 to frame routine 0xE2E00 at 0xAD9D4. The frame stores those three signed 64-bit camera values at renderer+0x338/+0x340/+0x348 and the supplied mesh radius at renderer+0x438, with the radius store at 0xE2FE1. Renderer source demand is therefore centred on these camera fields, not on an assumed identity with the player/destination samples used by the background workers.

Within the ordinary frame, 0xECDA0 scans the inclusive camera-zone square extending the renderer radius on both axes. Its regional passes inspect missing/null source entries and resident zones without active groups, then inspect existing active groups and costs to derive visibility parameters. These are source-map reads and visibility calculations at those passes, not source-zone generation requests. This contract does not re-specify the adaptive visibility arithmetic or its broader special-state branches.

The later zone-collection path in 0xD3170 uses that same inclusive camera-zone square when frame flag bit 0x80 is clear. It looks up already resident zones, requires a nonzero active-group-list count at zone+0x1D0, and applies bounds/distance/frustum helper 0xE0680 at 0xD37D5 before appending the zone pointer to the frame vector at renderer+0x300 at 0xD37FB. The frame resets that vector's end before rebuilding it. The helper uses the current prepared visibility value with a 64-block addition in this path; the complete frustum planes and distance equations remain outside this retention audit. Bit 0x80 suppresses this regional collection path. None of those local admission tests is an extra source-retention predicate in 0x2D2410.

Water pass 0xE85E0 subsequently traverses renderer+0x300/+0x308 and each collected zone's active groups, while other frame passes consume their prepared queues. A visible-zone collection, a mesh candidate, a complete neighbourhood and a resident source zone are therefore different observations. The inspected frame collection does not generate a missing source zone or make a source-zone lease. Other preparation consumers and alternative render callers are not exhaustively classified.

The host World uses an independent exact membership set. Each 0xF2340 cycle snapshots centres from its World+0x40 entity list under that World's +0x3C8 guard. The direct qualification at 0xF2414 is entity byte +0x60 equal to zero. State byte +0x68 equal to 0x9C chooses signed 32-bit block destination +0x1B0/+0x1B4; otherwise signed 64-bit position +0x10/+0x18 is truncated toward zero to blocks at 0xF2462 through 0xF2485. This is the proved host/player-source predicate; the audit does not generalize it into an all-and-only network-player classification.

For each captured host centre, the required-set builder considers both-axis zone coordinates obtained by flooring the centre minus 270 blocks and centre plus 270 blocks by 64, inclusive. It also requires each zone offset from the centre's containing zone to have absolute value below 6 and their squared-distance sum to be at most 25. The image double at 0x43FD20 is 25. The required set is the union of these per-centre rectangle/circle intersections; duplicates collapse into the set. It is not described as an unconditional 11 by 11 square or as the client view-distance window.

At 0xF2718 the host worker calls 0x2D2670 with this required set before generating its missing members. That routine collects loaded-map entries absent from the set while holding +0x3F0, then processes every collected removal. For each it acquires +0x3F0 and then +0x3C8, erases the map entry at 0x2D2892, preserves selected state through 0x2D3E20 at 0x2D289D, releases both guards and invokes the zone's deleting virtual. This host routine has no eight-zone removal cap. An empty required set can therefore retire all currently loaded host source zones on this path.

After this retirement phase, the host worker considers absent/null required members for its distance-key candidate vector, orders and truncates that vector to at most four entries, then calls 0x2AE0C0 serially at 0xF2CBE for the retained batch. The full priority-key/tie calculation is not re-audited. It sleeps 5 milliseconds when there is no candidate and yields after the batch. Unlike the client's source batch, this inspected host call loop does not dispatch the four entries through the client parallel-generation helper. Its next required-set snapshot follows completion of these serial calls and loop cleanup. Host membership retention itself performs no generation; generation is the later explicit missing-member phase.

The client loops inspect Game+0x2068 for continuation and standalone byte RVA 0x5514C7 for their pause path. A nonzero pause byte causes a 100-millisecond sleep instead of their normal cycle work. These checks are at loop boundaries; no arbitrary mid-batch cancellation or universal frame pause is inferred. On mesh-worker exit, call 0x84F2F reaches 0x2D2930, which empties that client's loaded map and later preserves/deletes the removed zones. The host loop has its separate continuation byte at host+0x550. Its full teardown and every alternate source-map eraser are not audited here.

The proved policies do not promise a fixed resident-zone count, complete prefetch of the retention region, automatic neighbour generation, prompt eviction under all movement rates, or one shared scheduling barrier across client loading, meshing, rendering and the host. Raw snapshots are not themselves ownership. Live changes between centre capture, generation admission and retirement, duplicate-generation races, overflow/extreme-coordinate cases, other source owners/callers and untraced writes or erasures remain explicit limits. No replacement-engine retention policy or implementation assumption is imported into these Steam facts.
