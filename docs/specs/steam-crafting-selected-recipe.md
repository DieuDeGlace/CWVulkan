# Native crafting selected-recipe publication and consumption

This bounded contract is FINAL / STABLE / HELD following author readback. Its supported image is cubeworld.original.exe.unpacked.exe, AMD64 PE32+, image base 0x140000000, 5,757,952 bytes, SHA-256 7AF18CB28C8BF848F355287428C6390B2EA2A682CA466190F5EB9859C5D6F244. Evidence consists solely of the original binary, original native function decompilations, the longer-budget original frame decompilation, assembly.txt and calls.csv after the standalone author policy. No other project prose or implementation material supplied evidence. All addresses below are RVAs. The scope is the directly inspected collection, selection, click, visibility, draw and frame edges; it is not a complete writer, callback or thread census.

Three independently retained states must be distinguished. The crafting list at Game+0x340 stores a selected group/row pair. The details/craft-button widget at Game+0x348 owns a copied recipe and its own publication pair. Game itself can own a further recipe snapshot for an in-progress crafting action. Changing the list pair alone does not, in every inspected path, replace either of the other two states. Draw regenerates presentation and eligibility from the details widget's retained recipe and live world/inventory state; it does not regenerate that recipe from the list pair.

Original UI construction 0xf9ac0 allocates 0x2d0 bytes for the list, constructs it through 0x27c950 with mode two and four tab controls, then allocates 0x390 bytes for the details widget and constructs it through 0x26bf70. The latter receives native resources named itemshadow, craftbutton and craftbar. The interface begins at Game+0x118; its pointers at +0x228 and +0x230 therefore correspond to Game+0x340 and +0x348. Routine 0x103200 binds the list's collection pointer at list+0x1e8 to the outer collection header at Game+0x17a8. This is a borrowed binding to the Game-owned collection, not ownership of a recipe-temporary allocation.

List constructor 0x27c950 initializes its selected pair at +0x278/+0x27c to two zero-valued four-byte integers. The separately maintained hover pair is +0x270/+0x274 and initially contains minus one in both components. The selected tab at +0x2b4 initially contains zero. The selected pair identifies an actual group and row in the collection, not merely a displayed cell or an address into a row allocation. List draw 0x27d2b0 resets and fills the hover pair as it encounters hovered rows. It does not copy a hovered recipe into the details widget in its inspected body.

Details constructor 0x26bf70 initializes an empty item value at +0x1f8, a zero four-byte recipe scalar at +0x298, an empty ingredient vector at +0x2a0/+0x2a8/+0x2b0 and a publication pair of minus one/minus one at +0x2b8/+0x2bc. The vector slots are begin, end and allocation-end. Its records have stride 0xa4, with an item value occupying the first 0xa0 bytes and a four-byte required quantity at +0xa0. The item, scalar and vector together have the same relative organization as the 0xc0-byte recipe record passed to the inspected recipe assignment helpers: item at zero, scalar at +0xa0, vector header at +0xa8/+0xb0/+0xb8. These are value-field and container boundaries, not a claim that every padding byte is initialized or semantically copied. The details widget borrows Game through +0x2c0 and stores its resource pointers at +0x2c8 through +0x2e0. Its draw eligibility byte at +0x38c initially contains zero.

One publication writer is the collection filler 0xb2ee0. For each generated recipe, it compares the filler group and current row ordinal with the list pair at Game+0x340, +0x278/+0x27c. A match copies the generated item value and four-byte scalar into the details widget, copies the ingredient elements through 0x82f10 and records the current selected pair at details+0x2b8/+0x2bc. This publication uses the temporary full recipe, not a pointer into the retained list's 0xa4-byte quantity/item row. There is no requirement here that the newly calculated craftable quantity be positive before publishing. The ingredient vector is an independently owned copy, so later destruction of the generated temporary recipe does not invalidate it.

That filler has no unmatched-selection clearing branch. If the selected pair does not match any generated recipe, its normal iteration leaves the prior details recipe and publication pair untouched. The caller 0xb2180 fills groups zero through five, then performs its remaining collection/layout work; it does not add a general missing-selection repair after those fills. Its outer-inventory-empty early skip also does not clear the details widget. Consequently a collection rebuild is not, by itself, proof that the details recipe corresponds to a currently valid selected pair. In particular the inspected calls of this filler do not provide a selected-group-six publication path.

The other directly established publication writer is mouse-button handler 0x94900. The window-message dispatcher 0x133c70 calls it with button number zero for message 0x201, establishing an ordinary left-button-down path. At entry the handler first invokes interface input dispatch 0x101020. For button zero that dispatch reaches 0x340ec0, which sets the UI left-button state and can synchronously invoke the applicable UI callbacks. The crafting publication branch comes later in 0x94900 and requires the crafting list's active control-state value to be nonzero. Thus a callback can affect the selection before that later branch evaluates it; this is not proof that every possible callback necessarily runs or succeeds.

At callsite 0x96260 the handler invokes 0x280e30 on the crafting list with its byte flag true. That helper requires a nonnull bound collection; if the hover-row component is negative it returns without replacing the selected pair. Otherwise it copies the hover group/row into selected +0x278/+0x27c and updates the selector presentation. Returning early for no hovered row does not itself cancel the caller's subsequent recipe publication. The caller then evaluates the selected pair that remains in the list.

Routine 0x94900 checks both selected components against zero and checks the selected group and row against the actual Game+0x17a8 collection bounds. An invalid pair publishes an empty item, zero scalar and empty ingredient vector through 0x834a0 at 0x96466, and sets the details publication pair to minus one/minus one. This branch does not rewrite the list's invalid pair into a valid selection. For a valid pair, the handler constructs a temporary recipe through 0x7ea10 and asks 0x2aec30 to generate recipe details from the selected row's item value at row+4, with World as owner/context. It does not obtain the recipe scalar or ingredient list by copying the displayed row, which contains neither of those full recipe fields. A true low-byte result publishes the generated recipe with 0x834f0 at 0x96366 and copies the selected pair into the details publication pair. A false result publishes a newly empty recipe through 0x834a0 at 0x963c1 and records minus one/minus one. The valid-pair branch does not first require the row's carried/craftable quantity to be positive.

The ordinary copy helper 0x834f0 copies the item value and four-byte scalar and assigns the ingredient vector through 0x82f10. That vector assignment copies 0xa4-byte element values, reusing or replacing destination storage as needed; it does not retain the temporary source vector. Temporary recipes are cleaned through 0x81870 after publication. The empty/reset assignment 0x834a0 instead uses vector helper 0x82e80: it releases the destination's old ingredient allocation, takes the source header and empties that source header. Its inspected reset callers supply empty temporary vectors, so their completed reset leaves no live ingredients. These different value-copy and storage-transfer edges must not be conflated with borrowing a temporary recipe. Allocation failure/exception atomicity and a transactional multi-field publication guarantee are not established by this audit.

Tab changes have separate list behavior. Tab callback 0x27f980, installed by 0x280440, accepts a nonnegative hovered tab below the bound outer collection's tab count and acts only when it differs from the current tab. Routines 0x27f830 and 0x2802f0 advance or retreat the current tab with wraparound over the widget's tab-control count; the original ordinary input loop 0x1355a0 calls them for the crafting list as well as other lists. These paths refresh layout, set selected group/row to minus one/minus one for an observed empty target group, or select the target group and the first row on its stored page for a nonempty group. The latter row is a canonical row ordinal derived from the page, not a full copied recipe. These routines refresh selector/scroll presentation and notify 0x9de90, but that notifier immediately returns for widgets other than Game+0x350; it is not the crafting details publisher for Game+0x340.

None of those inspected tab routines directly assigns details+0x1f8, +0x298, its ingredient vector or its publication pair. A tab mouse callback can be followed by the later 0x94900 publication branch on the same ordinary left-button-down dispatch. The advance/retreat tab paths alone do not contain that publication edge. Programmatic selector helper 0x89580 likewise changes the list tab, selects that tab's row zero, clears the hover pair and refreshes layout/selection presentation without directly assigning the details recipe. Original interaction handler 0x98180 has several paths that call 0x89580 and then 0xb2180, supplying a different way for a changed pair to be followed by filler publication. This does not make selection changes universally self-publishing.

Showing/hiding also has multiple effects. The crafting-menu callback 0x102f10 toggles the list control-state value and calls 0xb2180 at 0x102f56 on both toggle directions; its later layout/scroll work occurs only when the list is active afterwards. Therefore hiding through this callback can still run the matching filler publication, while an unmatched rebuild can retain old details. In frame 0xa5a50 the details control-state value is copied from the list's control-state value through 0x9af00 and 0xa3a20 at 0xab0ae and 0xab0b9. The inspected visibility setters only write that state; they do not destroy the details recipe or free its ingredients. Other observed frame hide paths similarly set both control-state values to zero without directly clearing the widget's retained recipe.

The details widget's vtable at image RVA 0x46d3c0 identifies 0x26c2d0 as its ordinary draw entry. Draw first resolves the retained output item through 0x173b10 using Game->World+0x70. If resolution returns zero it returns before its later hover reset, ingredient presentation and eligibility writes. That early return is not a missing-selection repair and does not establish that a previously written eligibility or hover value has just been cleared. For the ordinary continued draw path, +0x2e8 is reset to minus one and the hover item at +0x2ec is marked empty, then populated by copied output/ingredient item values under the appropriate hit regions. Getter 0x94580 can expose this widget-owned hover item while the details control-state is active; it is not a borrowed pointer into the recipe temporary or the list collection.

Continued draw reads the retained item and ingredient vector for icons and text, regenerates the item-name presentation through 0x1628b0 and reads the live actor/inventory to calculate available ingredient quantities. It compares these live totals against each retained ingredient's four-byte required quantity. It also reads scalar +0x298 as a requirement selector; the native presentation includes requirements such as water, furnace, anvil, spinning wheel, loom, saw, workbench and campfire. The scalar is therefore observed as a requirement code in this consumer, not the list's calculated craftable count. Subject to the resource/control checks, requirement and ingredient results together with the craft-button hit-test result determine the byte at +0x38c. Draw also presents progress from Game+0x20cc through the craft-bar resource. It does not call 0x2aec30, rerun the selected-recipe filler, validate the details publication pair against the list pair or replace the stored item/scalar/ingredients in its inspected body. The complete spatial requirement algorithms and all draw-side effects are outside this contract.

The frame consumer 0xb03d0, called from frame at 0xaaef7, distinguishes the details control-state from the recipe value. When that state is zero, it resets the progress at Game+0x20cc to minus one, installs an empty recipe in Game's action snapshot and records action pair minus one/minus one. This clears Game's action snapshot, not the details widget's recipe. When the details state is nonzero, the consumer uses the stored eligibility byte +0x38c and UI left-button-state bit at Game+0x20, +0x1a8. On the inspected eligible-held path, a negative progress value starts a new action: 0x834f0 at 0xb046c copies the details recipe into Game+0x20d8, and the widget publication pair is copied into Game+0x2198/+0x219c. The snapshot scalar is Game+0x2178 and its owned ingredient header is +0x2180/+0x2188/+0x2190. For certain output categories, the snapshot output's region coordinates are then replaced with the current actor region; that is a snapshot mutation, not a rewrite of the details recipe.

Once progress is nonnegative, this body does not continually recopy a newly selected recipe into that action snapshot. Selection changes or a later widget publication can therefore coexist with an already retained action snapshot until the observed action/reset boundaries. When eligibility or held state is absent, the inspected active-widget path changes the progress rate; it does not immediately erase the action recipe or necessarily cancel nonnegative progress. Completion reaches 0x8fbc0 at 0xb0545, which reads the Game snapshot item, ingredients and action pair, performs its crafting effects and calls 0xb2180 near its normal end. This final rebuild can republish a matching details recipe; the frame consumer itself does not regenerate a full recipe from the list pair on every frame. Routine 0x26e940 only updates the progress-bar resource from the supplied progress value in its inspected body.

Widget destruction 0x26c220 releases the ingredient allocation through 0x51070 and clears its three header slots before base cleanup. Deleting wrapper 0x26c290 additionally frees the widget allocation when the low deletion-flag bit is set. Temporary recipe cleanup 0x81870 releases that temporary's own vector, and vector replacement can invalidate addresses into previous destination storage. These normal ownership paths establish independent value lifetimes for generated temporaries, the details recipe and the action snapshot; they do not establish safe concurrent destruction or borrowing across replacement.

The observed frame consumer and its nearby frame-driven rebuild/visibility calls lie in the World+0x3c8 critical-section interval entered by 0x2abb70 at 0xa6464 and left by 0x2b9890 at 0xadb23. Those two helpers directly address the inline critical section at World+0x3c8. The inspected recipe-copy/filler/draw bodies do not independently establish that interval. The ordinary window-message dispatch to 0x94900 does not itself acquire it. The handler contains a separate acquired-and-released World interval for an unrelated item action earlier in its body; that does not extend over the later selected-recipe publication branch. No universal UI-thread serialization, complete transitive lock coverage, complete writer inventory, freshness guarantee, indirect callback closure or exception-lifetime guarantee follows. Missing selections are cleared on the specified mouse-publication branches; they can remain stale on unmatched rebuild or selection-only paths. These are bounded original behaviors, not a replacement-engine implementation prescription.
