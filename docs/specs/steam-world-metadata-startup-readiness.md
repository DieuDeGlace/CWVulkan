# Native World metadata startup readiness

This bounded contract is FINAL / STABLE / HELD following author readback. The supported original image is cubeworld.original.exe.unpacked.exe, AMD64 PE32+, image base 0x140000000, 5,757,952 bytes, SHA-256 7AF18CB28C8BF848F355287428C6390B2EA2A682CA466190F5EB9859C5D6F244. Evidence is restricted to that original binary, original function decompilations including the longer-budget frame retry, assembly.txt and calls.csv after the standalone author rules. No other project prose, implementation, SDK, tests, captures or implementation history supplied evidence. All routine and instruction addresses below are RVAs.

The ordinary startup path establishes the active client World's seed and day metadata before the completed Game object is supplied to the frame loop. This happens inside Game constructor 0x7ea80 and does not depend on successful saved-character loading or character selection. World construction alone does not provide the same established metadata state. There is no independently established universal metadata-ready bit or predicate covering arbitrary World objects and arbitrary observation times.

The three fields have distinct established widths and sources. World+0x220 is four bytes receiving the setup routine's 32-bit seed input. World+0x244 is a four-byte integer derived during seeded random setup. World+8 is a four-byte day/counter field, used with signed integer arithmetic by the native day updater. Its adjacent field at +0xc is a four-byte floating-point time value. Initialized here means the stated native writes have completed; it does not mean that every World byte is initialized, that a saved value has passed additional semantic validation, or that the object has a universally safe lifetime.

Startup routine 0x1355a0 allocates the ordinary client World separately, using 0x548 bytes, and calls constructor 0x29a130 at 0x136163. It subsequently constructs the World map with that World pointer and supplies the same World as the second argument to Game constructor 0x7ea80 at 0x136331. Game stores this supplied pointer at Game+8. This establishes the ordinary active-client access path; the pointer store alone is not a refcount acquisition or proof of ownership transfer.

Constructor 0x29a130 constructs collection headers, identity-string storage, helper objects and native critical sections. Its call to 0x29af50 with destination World+8 constructs the collection portions of the state aggregate, but that nested initializer does not write its first eight bytes, which are the enclosing World's day and time slots. No primary-seed, derived-seed or day value is established by the constructor writes inspected here. The ordinary allocation caller does not first clear the complete World allocation. A nonnull result from this constructor therefore cannot substitute for evidence that setup has completed. The constructor does establish an empty identity string at World+0x200 and a zero byte at +0x358; that byte is later tested for behavior selection, not established as a setup-completion marker.

Game constructor 0x7ea80 initializes a requested seed value of decimal 123 at Game+0x206c; the corresponding instruction is 0x7ef6a. It constructs the narrow identity text "world" at Game+0x2070. At 0x7f279 it calls setup 0x2b5f20 with the current World from Game+8 in RCX, the four-byte requested seed in EDX and the identity-string address in R8. This call precedes character-database opening at 0x7f32e and interface construction at 0x7f4d4. Thus these metadata writes do not await a selected character or an inferred character-loading milestone.

Setup 0x2b5f20 writes the primary seed at World+0x220 at instruction 0x2b5f76 and copies the supplied identity text into World+0x200. It seeds the native random runtime and initializes additional World-owned values and storage. The derived seed is written to World+0x244 at 0x2b61f6. Near the end of the normal setup path, it writes day 1 at 0x2b66f7 and time bits 0x4c095440 at 0x2b66ff. These are separate writes with substantial work between them. Seeing the primary seed already match a requested value is not evidence that derived-seed and day initialization has finished.

The setup routine can then restore saved state before returning. When World+0x358 is zero and the supplied identity string is nonempty, it opens the original "Save/world.db" path and calls 0x2b98b0 at 0x2b676d. That routine requests the "state" entry and, when present, passes an input reader and destination World+8 to 0x148e90. The latter can replace the four-byte day and four-byte time values after its input-length checks. Its observed destination writes and collection operations concern this state aggregate, not the primary/derived seed slots. Consequently a normally completed startup World need not still contain day 1: day/time may have come from saved state. Failure to find the state entry does not undo the defaults already written. Full malformed-input, exception and validation behavior is outside this startup qualification.

The Game constructor continues by creating a placeholder Creature, configuring it and installing it as the current actor at World+0x448. It invokes World preparation 0x2e0b50 at 0x7f662. Only afterwards does the optional saved-character branch try to select and load a previously recorded character. That branch may perform further actor/interface work, but its absence does not bypass the earlier World setup or placeholder installation. This is the direct basis for applying the metadata ordering to title-menu operation without assuming that a character has loaded. This note does not assign an undocumented semantic meaning to every menu or interface flag.

There is also a distinct hosted World. Early in Game construction, call 0x7eb36 invokes hosted-object constructor 0xf17a0 for the inline object at Game+0x6e8. That constructor invokes 0x29a130 for its own inline World at hosted-object+8, hence Game+0x6f0. It calls 0x2b5f20 at 0xf1969 with seed 123 and its own supplied identity text, before the later thread-construction operation at 0xf19e8. This World is not the separately allocated client World accessed through Game+8. Initialization of either object must not be inferred merely from finding the other. No equality of their derived seeds or saved state is asserted here.

On successful ordinary startup, routine 0x1355a0 stores the return value of the completed Game constructor into the process's Game pointer slot at image RVA 0x551a80. That store is instruction 0x13633e. The ordinary message/frame loop later invokes wrapper 0x134420 at 0x137b8e; that wrapper calls frame 0xa5a50 at 0x134558. This establishes program order for the ordinary startup/frame path. Constructor exceptions, partial construction and arbitrary external observation during the constructor do not gain a completed-setup guarantee from this ordering.

Wrapper 0x134420 tests the globals at image RVAs 0x551a90 and 0x551a80 for nonzero values before its frame call; the tests are visible at 0x134433 and 0x134441. These are the directly observed wrapper conditions. They do not themselves inspect primary seed, derived seed or day, and they are not a standalone metadata-validation predicate. The stronger startup fact is that the ordinary Game pointer assignment occurs after the constructor's completed setup call, rather than that a nonnull World or Game pointer inherently means readiness.

Frame 0xa5a50 has a separate identity-agreement condition for World simulation advancement. It loads the current World through Game+8, reads World+0x220 at 0xa72d2 and compares it with Game+0x206c at 0xa72e1. If the bits agree, it compares Game+0x2070 with World+0x200 through string-equality helper 0x6dd20 at 0xa72f8. Agreement permits the calls to World update 0x2da6c0 at 0xa7328 and 0xa734c. A mismatch skips those calls. This condition reads the primary seed as part of the decision; it does not first validate all three metadata fields, test a setup-completion bit or enclose every other frame access to the World.

The update path reaches 0x2e2e80, which reads and advances the time field and can increment the signed day at World+8. On the ordinary initial path, the prior completed setup has already supplied those values, possibly including the saved-state override. A separate demonstrated derived-seed consumer is Zone creator 0x2ae0c0: on its creation path it reads World+0x244 before reseeding the random runtime and constructing/generating a Zone. This establishes an actual use of that derived field. The exact first derived-seed read across every startup worker and descendant is not established here; this note does not claim that the first frame necessarily creates a Zone.

The identity condition is also distinct from later requests to change the active identity. Routine 0x8a500 writes a requested seed and string at Game+0x206c and +0x2070 while holding the current World's critical section, and performs other current-World work. Its inspected body does not initialize World+0x220 or +0x244 to the new request. Therefore requested-identity agreement and current-object metadata initialization are different facts. This bounded startup audit does not qualify every later network transition, reseed, object replacement or packet writer.

Observed protection is specific. Constructor 0x29a130 initializes the World critical sections before the later startup setup call. Setup 0x2b5f20 has no established general World+0x3c8 critical-section interval of its own, and its separate field writes are not an atomic publication. In the observed frame path, helper 0x2abb70 enters the current World's critical section at +0x3c8 at 0xa6464; the identity comparison and update calls occur inside the interval ending with 0x2b9890 at 0xadb23. These helpers directly enter and leave that native critical section. This is a caller-held scope, not evidence that every reader/writer uses it or that arbitrary constructor-time observations are safe.

The established readiness boundary for the ordinary first-frame path is completed Game construction containing completed World setup, followed by the ordinary Game-pointer assignment and frame invocation. The title/selection path shares that setup ordering. World construction, a nonnull pointer, an early primary-seed match and a presumed loaded character are each weaker observations. Universal worker synchronization, transitive constructor exposure, complete failure cleanup, later active-World transitions and a general lifetime/readiness predicate remain unresolved. No capture policy, replacement-engine gate, universal lock order or disposal rule is prescribed.
