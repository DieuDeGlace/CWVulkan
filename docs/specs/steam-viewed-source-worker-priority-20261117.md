## Launch and option source

The ordinary startup routine at RVA 0x1355A0 reads options.cfg through RVA 0x13AA50 before constructing the game object at RVA 0x7EA80. The options initializer at RVA 0x13A9E0 sets the signed 32-bit field at options offset +0x18 to 1. The loader for the saved file reads cpuPerformance into that field as an integer. Game construction copies it to game-object offset +0x1BA0 before starting the viewed loader. The CPU Usage display at RVA 0x288C50 shows REDUCED for zero and FULL for a nonzero value. Its option callbacks at RVAs 0x28B160 and 0x28B170 assign 0 and 1 in the menu data. The apply path at RVA 0x89C10, reached through RVAs 0x28B140 and 0x28B350, copies that option to the game object under the world critical section used by the loader.

The game constructor calls the viewed loader's launcher at RVA 0x7F80F. The launcher at RVA 0x762D0 calls MSVCP140's thread-start import at RVA 0x76390 with thread output storage, a runtime entry callback at RVA 0x3C7D0, and a launch record holding game state. The callback dispatches through RVA 0x437EB8 and the jump at RVA 0x87BF0 to RVA 0x89160. That wrapper signals its startup handoff and releases the handshake mutex before calling the loader at RVA 0x84F70. The handshake marks receipt of the launch record. The launch arguments and wrapper supply no priority, affinity, process class, or caller priority read. The first explicit priority request for this thread occurs inside the loader.

## Requests and timing

On entry, RVA 0x84F70 gets its own thread handle at RVA 0x84FC8 and submits priority −1 at RVA 0x84FD4. It then constructs a scheduler policy, supplies minimum concurrency 1 and maximum concurrency 4 at RVA 0x84FF2, sets policy key 6 to the unsigned representation of −1 (0xFFFFFFFF) at RVA 0x85005, and submits this policy to CurrentScheduler::Create at RVA 0x8500F. These calls precede the loop gates and the first CPU Usage read. The last-observed option is seeded to 1 after the create call, independently of the loaded value.

At the start of each enabled pass, the coordinator reads the full 32-bit CPU Usage value at RVA 0x85068 while holding the world critical section. A value different from the last observed value triggers the self-thread priority request at RVA 0x8508B, followed by fresh policy construction, concurrency limits at RVA 0x850B1, key 6 at RVA 0x850C4, scheduler creation at RVA 0x850CE, and destruction of that temporary policy value at RVA 0x850D9. The request precedes candidate selection and can occur on a pass with no candidates. The new integer is carried forward for comparison on the next enabled pass. A disabled pass at RVA 0x85040 takes the 100 ms sleep path without taking an option sample. The loop runs while the byte at game-object offset +0x2068 is nonzero.

A change between distinct nonzero integers submits a fresh policy even though the requested arguments match. For 1 to 0 on a run that started at 1, the first update repeats the startup arguments. The later return to 1 submits the 0 priority and maximum concurrency 8. A mode write reaches the priority path through the coordinator's next enabled comparison. The game calls do not establish a delivery deadline or a separate setter call for an intermediate value missed between samples.

## Selected work

The coordinator limits each selected batch to four source entries before calling the dispatcher at RVA 0x7D5C0. With exactly one entry, the dispatcher calls the source-generation routine at RVA 0x2AE0C0 inline on the coordinator at RVA 0x7D618. This route executes on the thread targeted by the coordinator's self-priority request and makes no task submission for the single entry. On the multiple-entry route, RVA 0x76DA0 queries the current scheduler's virtual processor count at RVA 0x76E14, partitions entry ranges using that count and the batch size, and submits all but the last partition through the structured task collection's scheduling call at RVA 0x76FD8. It supplies the final partition to the collection's run-and-wait call at RVA 0x77073. The application submits the scheduler context policy ahead of this route and queries the current scheduler when the batch is dispatched. The game passes no individual lane priority or OS thread handle at these task submission sites. A scheduler limit of 8 leaves the four-entry selection cap in force.

The chore entry at RVA 0x75B80 reaches RVA 0x858E0. A one-entry partition calls the same generation routine in its executing context. Larger partitions can schedule and wait for nested chores. The task handoff paths at RVAs 0x85C5A and 0x88742 use the Concurrency Runtime spin-wait with a yield callback. The executing chore waits for its nested collection at RVA 0x85CC6. The coordinator waits through the outer call at RVA 0x77073 before the batch returns. The coordinator then calls Sleep with zero at RVA 0x855DE. An empty enabled pass sleeps for 5 ms at RVA 0x85555 before the same zero-duration sleep. These wait and yield calls have no priority argument and perform no caller-side priority write.

## Other caller evidence and runtime limits

The same startup caller launches a separate coordinator first, through the call at RVA 0x7F7C2 and the launcher and callback at RVAs 0x76160 and 0x890C0. The reached routine at RVA 0x842D0 also reads the shared CPU Usage field. It seeds its own comparison to 1 and performs no explicit startup thread-priority or scheduler-policy submission in its entry path. On its own observed change it applies the same zero or nonzero mapping to its own current thread and its own scheduler creation call at RVAs 0x844BB through 0x844FF. This proves a second ordinary caller sensitive to the option. Each coordinator's request depends on its own observation of the field. The traced calls contain no game-side read of another thread's priority, write to the other coordinator's handle, or decision based on another scheduler or priority winner.

The evidence establishes the application's submitted arguments and synchronization calls. Both viewed-loader thread-priority submissions leave the OS return unchecked. The original calls give no readback of effective priority, guarantee of scheduler creation or runtime attachment behavior, explicit scheduler detach, or proof of priority effects on particular OS worker threads. Runtime policy defaults and lifecycle, any pre-entry inheritance, dynamic priority adjustments, process class, priority boosts, affinity, actual simultaneous lane count, OS thread assignment, run or completion order, and the effects and duration of waits and yields remain outside this evidence. The launch handshake gives no guarantee that the loader has reached its first priority call before the launcher returns.
