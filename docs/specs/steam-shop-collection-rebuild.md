# Native shop retained collection and rebuild

This bounded contract is FINAL / STABLE / HELD following author readback. The supported image is cubeworld.original.exe.unpacked.exe, AMD64 PE32+, image base 0x140000000, 5,757,952 bytes, SHA-256 7AF18CB28C8BF848F355287428C6390B2EA2A682CA466190F5EB9859C5D6F244. Evidence is restricted to the original image, original native function decompilations, the longer-budget original frame decompilation, assembly.txt and calls.csv after the standalone author policy. No other project prose, implementation, SDK, test, probe or capture supplied evidence. Addresses below are RVAs. The audit covers rebuild 0xb75d0, its four directly selected stock routines, retained buyback input, selected UI/event edges and normal value ownership. It is not a complete stock-generation, writer, RNG, callback or lock census.

The shop collection is retained in Game, while its current contents are rebuilt on specific original paths. It is not a retained pointer to a merchant's inventory. A rebuild destroys the previous copied row collections before selecting its input. Tab one copies retained Game buyback history into group one. Every other tab value takes the merchant-stock branch, which normally populates group zero. Both groups exist on normal completion, but the inactive group's previous copied rows are not preserved. Draw uses this stored collection without directly invoking the rebuild in its inspected body.

The outer vector header is Game+0x1870 begin, +0x1878 end and +0x1880 allocation-end. Constructor 0x7ea80 initializes all three slots to zero. Each outer element has stride 0x18 and is itself a begin/end/allocation-end header. Its row stride is 0xa4: a four-byte quantity at row+0 and an inline item value beginning at row+4 with storage span 0xa0. Counts are not 16-bit notice quantities. Original insertion 0x4e810 and shop consumers use four-byte counts and signed tests; minus one is a stored special stock quantity, distinct from a zero count. These are field/storage boundaries, not a claim that item padding bytes are all initialized or copied as opaque bytes.

Original interface construction 0xf9ac0 allocates 0x2d0 bytes for the widget at Game+0x350 and calls 0x27c950 with mode three. The interface begins at Game+0x118, so its widget pointer +0x238 corresponds to Game+0x350. Two tab controls receive native resource bindings named vendor-buy and vendor-undo, in that order, through 0x280440. Routine 0x103200 binds widget+0x1e8 to the outer header at Game+0x1870. This is a borrowed pointer to the Game-owned header; the widget does not acquire ownership of those row buffers. The widget constructor initializes selected tab +0x2b4 to zero, selected group/row +0x278/+0x27c to zero/zero and hover group/row +0x270/+0x274 to minus one/minus one.

Callable entry 0xb75d0 receives Game in RCX. Its first operations call 0x372c0 over all currently live outer elements, then reset outer end to outer begin and resize to two empty elements through 0x64f30. Helper 0x372c0 releases each inner row allocation and zeros that inner header. The outer allocation can be retained or replaced by vector growth; the initial clear is not just an end-pointer reset that preserves old row allocations. A final 0x64f30 call again sets the normal outer live size to two. There is no old-stock preservation branch for a failed merchant lookup.

The selected-tab test is equality with one, not a general range validation. When the tab is one, the rebuild uses Game+0x21b0 and does not perform the merchant lookup or call one of the four stock generators. This history is a doubly linked list whose header contains an eight-byte sentinel pointer at Game+0x21b0 and an eight-byte node count at +0x21b8. The ordinary constructor initializes a self-linked sentinel through 0x87080 and a zero node count. Nodes have allocation span 0xb8, next and previous links at +0 and +8, and a copied 0xa4-byte quantity/item payload beginning at +0x10: four-byte quantity at +0x10 and item at +0x14. Helper 0x6e5b0 copies that payload into a newly allocated node rather than retaining an inventory-row pointer.

Buyback rebuilding walks this list backwards from sentinel.previous and appends each payload through 0x61020 to group one. The source quantity is copied as four bytes, and the item is copied by value through 0x35400. There is no local zero-quantity, item-category, merchant-identity or duplicate filter in this copying loop. It does not merge equal items. The retained row order is the reverse of forward list order. In the inspected ordinary sale paths, records are appended at the list's back, so the rebuilt display order places the most recently appended records first. The source list itself is not cleared, reordered or consumed by 0xb75d0. An empty source list produces two empty groups on normal completion, not retention of previous copied buyback rows.

For every tab value other than one, 0xb75d0 reads World from Game+8 and searches the tree whose sentinel/header pointer is World+0x450. Its search uses Game+0x1e98 as an eight-byte key with signed 64-bit ordering/equality. The inspected tree nodes have the key at +0x20, a pointer value at +0x28, links at +0/+8/+0x10 and sentinel marker byte at +0x19. A missing key or zero pointer value skips stock generation. Because clearing occurred first, the normal result then contains two empty groups. An empty merchant tree has the same cleared result, provided its sentinel and the other owner/UI prerequisites are valid. This is not a general null-World, null-sentinel or null-current-actor fallback.

The generator dispatch uses the four-byte value Game+0x1ea0. Value 0x81 calls 0x2acf90 at 0xb7704; value 0x82 calls 0x2ac6e0 at 0xb76fa; value 0x9c calls 0x2acbd0 at 0xb76f0; the other values use 0x2acdd0 at 0xb76e9. Assembly establishes the actual third argument omitted from some decompilation call displays: the first two routines receive the nonzero tree-resolved pointer in R8, whereas the latter two receive the address Game+0x1e98 in R8. RCX is World and RDX is the destination outer collection header. No merchant pointer is installed as a shop row or as ownership of the destination collection by these calls.

Routines 0x2acf90 and 0x2ac6e0 regenerate temporary item vectors, with item stride 0xa0, rather than copying a retained merchant stock vector. Direct inputs include the resolved object's low four bytes at +8, its two eight-byte fields +0x1b8/+0x1c0 used for coordinate-derived input, World day/counter +8, the current actor reached through World+0x448 and that actor's byte +0x14c. They obtain a generation bound through 0x2bb290, whose inspected path constructs and destroys a temporary region-role record using the current actor's two four-byte coordinates at +0x150/+0x154. These observations do not assign a broader semantic name to every merchant field or recreate the item generation tables.

Those two temporary item vectors are sorted through 0x299090 before stock insertion. The directly inspected insertion/partition/heap comparison paths, including 0x298300, 0x2987f0 and 0x298a00, compare item byte +0x14 as an unsigned value in ascending order, without an additional name/coordinate key. Small-span insertion preserves equal-byte order; a general stable ordering of equal values through larger partition/heap paths is not established here. Items are then fed to 0x4e810 with explicit destination group zero. This insertion can merge eligible equal item values rather than preserving one row per generated temporary. Thus the eventual row sequence is the insertion result from the sorted values, not a guarantee of an unchanged one-to-one temporary-item index.

The remaining stock routines 0x2acbd0 and 0x2acdd0 construct their own item values and insert into group zero in their observed native call order. The former has four finite-count insertion sites; the latter includes minus-one quantities and a finite-count generated choice. The finite-count paths consult 0x2a0c80 and clamp exhausted availability to zero before insertion. Routine 0x4e810 ignores an incoming zero quantity or empty item. For ordinary accepted values it stores the four-byte count, copies the item value and can combine stackable equal items; incoming minus one has its own overwrite behavior for an equal stackable row. The audit does not recreate the full stock-item catalogs or all item-equivalence rules.

The availability input read by 0x2a0c80 is separate from the UI collection and buyback history. It follows World+0x448 to the current actor, then actor+0x1528 to a structure whose tree header is +0x138. It searches by the supplied eight-byte merchant identifier and counts matching item values in the associated list using 0x4df60. This is a count of matching list entries, not a quantity read from the Game shop row. The inspected purchase path records an item value under the merchant identifier through 0x7bff0 and 0xa17d0 before rebuilding. Rebuild does not clear that availability history. Its full allocation/destruction lifetime and all writers are outside this bounded contract.

Rebuilding stock has explicit CRT RNG effects. The four stock routines use srand through image IAT RVA 0x42cd38 and rand through 0x42cd28, identified as API-MS-WIN-CRT-UTILITY-L1-1-0.DLL imports. In 0x2acf90 the seed uses the low four identifier bytes at resolved-object+8, the four-byte World+8 value multiplied by thirteen and constant 0x156b6; 0x2ac6e0 uses the analogous inputs with constant 0x10ec. Their srand callsites are 0x2ad02b and 0x2ac77b. Routines 0x2acbd0 and 0x2acdd0 use the low four bytes addressed by their identifier argument and the four-byte World+8 value multiplied by thirteen, with srand at 0x2acc06 and 0x2ace01. These are 32-bit multiply/add seed operations, not an eight-byte identifier hash.

Direct rand sites in 0x2acf90 are 0x2ad050 and 0x2ad0e4, and in 0x2ac6e0 are 0x2ac7a0 and 0x2ac834; these sites occur on loops, so site count is not runtime draw count. Their reached item builders 0x2d15d0 and 0x2d0680 also contain conditional rand calls. Routine 0x2acbd0 has direct rand sites 0x2acc5c, 0x2accb0, 0x2acd04 and 0x2acd57; 0x2acdd0 has one at 0x2ace96. No RNG-state restoration appears in those inspected stock bodies. The buyback copy branch and rebuild entry itself have no direct rand/srand import call; this does not certify the whole reached UI/helper closure as RNG-free or establish global/thread-local CRT behavior. These facts authenticate state and input dependencies, not a complete random-draw algorithm.

On every normal rebuild branch, including a missing merchant or empty buyback source, 0xb75d0 finishes by refreshing widget layout through 0x280a40 at 0xb771d and tail-transferring to scroll-thumb routine 0x280c80 at 0xb7733. These steps do not reset selected tab or selected group/row. Layout reads the bound collection, resizes per-tab page offsets and, for a valid empty selected group, sets page count +0x2a4 and that tab's page offset to zero. The thumb routine has its own nonnull-resource/nonempty-page-vector/nonzero-page-count gates; for page count zero its body does not perform the thumb geometry update. Therefore reaching the thumb entry is not proof that an empty rebuild resets its geometry or selector. The layout also reaches 0xb3ed0 on the player's carried inventory, so this refresh is not solely a read of shop storage. Mode-three shop refresh skips the mode-zero-only region-choice builder body reached through 0x2806a0.

An invalid selected tab is not silently normalized by rebuild. Exactly one selects the history branch; other values select stock generation, after which the normal outer size is still two. Later UI helpers do not provide a general negative-index guard. This note does not qualify arbitrary negative tabs or malformed widget/source state as safe successful calls. Even for valid tabs, neither rebuild nor its finishing layout/thumb entries repair a selected pair whose row no longer exists. A null bound widget collection does not prevent the earlier shop collection clear/generation; it only affects those later helper gates.

The tab callbacks supply an additional, precisely ordered rebuild edge. Routine 0x280440 installs callback 0x27f980 for hovered tab controls. It changes selected tab, refreshes layout against the currently retained collection, chooses minus one/minus one for an observed empty target group or chooses the target group and the first row on its stored page, then refreshes selector/thumb presentation. Advance/retreat paths 0x27f830 and 0x2802f0 perform the corresponding tab changes with wraparound. Only after that work do these routines call notifier 0x9de90. Original assembly at 0x9de97 establishes that the notifier tail-jumps to 0xb75d0 only when its widget argument equals Game+0x350; other widgets return. Thus these shop tab changes can regenerate stock or recopy buyback after the earlier selection decision. Since the inactive group's rows were cleared by the previous rebuild, that earlier decision can observe an empty group; the subsequent rebuild does not automatically repair the resulting minus-one pair.

The supplied direct-call records identify five CALL sites to 0xb75d0: 0x95251, 0x95d15, 0x96019 and 0x9619d inside mouse-button handler 0x94900, and 0x98f23 inside interaction handler 0x98180. The tail edge through 0x9de90 and its three inspected tab callers are additional established reachability, not direct CALL records to the rebuild. Interaction commit in 0x98180 recognizes object byte +0x14c values 0x80, 0x81, 0x82 or 0x9c, activates the shop, copies object identifier +8 into Game+0x1e98 and the zero-extended role byte into Game+0x1ea0, then rebuilds. It does not first reset the shop tab to zero, so an already selected buyback tab can take the history branch on this opening path.

The mouse-handler sites cover observed sale/history insertion, buyback consumption and ordinary stock purchase paths. Sale paths copy a quantity/item record into the Game history list, trim its oldest front node through 0xa0720 when the node count exceeds ten, then rebuild. Buyback consumption identifies the history node corresponding to the displayed reverse-order row, subtracts the number successfully restored to inventory and unlinks/frees a node when its remaining four-byte quantity reaches zero, then rebuilds at 0x96019. Ordinary stock purchase records the purchased item in the actor's merchant-keyed availability history and rebuilds at 0x9619d; the refreshed stock is regenerated with that input rather than merely decrementing a permanently retained merchant row. These are observed branches, not a claim that every purchase failure, item mutation, day change, merchant mutation or inventory event triggers rebuild.

Getter 0x94750 returns a pointer directly into the currently retained shop row item after its active-state/hit-test and group/row bounds checks. It does not return a separately owned item copy. Such a pointer is invalidated by a rebuild that frees the old inner allocation, even if allocation later reuses the same numeric address. The audit does not extend that borrowed lifetime merely because an original caller carries a pointer across other calls. In contrast, buyback nodes and generated temporary item vectors are independent source allocations; their values are copied into shop storage, and their addresses are not retained as rows. The generated temporary vector is released before the generating stock routine's normal return. Rebuild leaves the buyback source list intact. Ordinary Game destructor 0x818d0 destroys that history's nodes and sentinel and calls 0x4e7a0 for Game+0x1870; that helper releases inner rows, releases the outer header allocation and zeros the outer header.

The mode-three draw body at 0x27d2b0 reads the bound group rows, updates hover values and generates item-name/count/price presentation. It uses the distinct stock and buyback price consumers for the selected tab, and a minus-one row quantity can remain eligible even though positive-count suffix presentation has a different test. There is no direct call to 0xb75d0, 0x9de90 or one of the four stock generators in this draw body, and no inspected draw-side replacement of the shop collection. This supports retained-draw consumption, not a transitive proof that every formatter or generic callback is side-effect-free. The inspected frame body contains hide-state writes for the shop but no direct shop rebuild call.

Protection is caller-dependent. One established interaction chain is frame 0xa5a50 calling 0x8ae50 at 0xa9b2c, then interaction 0x98180 at 0x8df69 and potentially the opening rebuild at 0x98f23. That frame interval is inside the World+0x3c8 critical section entered through 0x2abb70 at 0xa6464 and left through 0x2b9890 at 0xadb23. The direct window-message path through 0x133c70 to mouse handler 0x94900 does not itself establish that same interval. The handler has an unrelated local World lock interval for another item action; it is released before later paths and is not a general guard around all shop rebuilds. Rebuild and the four stock bodies do not independently acquire a general World guard in their inspected code. No complete indirect caller, concurrent writer, RNG, publication, exception-cleanup or universal lifetime guarantee follows. The contract describes bounded original retention and refresh behavior and prescribes no replacement implementation or capture policy.
