# Native crafting tab-control lifetime and group mapping

This bounded contract is FINAL / STABLE / HELD following author readback. The supported image is cubeworld.original.exe.unpacked.exe, AMD64 PE32+, image base 0x140000000, 5,757,952 bytes, SHA-256 7AF18CB28C8BF848F355287428C6390B2EA2A682CA466190F5EB9859C5D6F244. Evidence consists only of the original image, original native function decompilations, assembly.txt and calls.csv after the standalone author policy. No other project prose, implementation, SDK, tests, probes, captures or handoffs supplied evidence. All addresses below are RVAs. The scope is the directly established crafting registration/replacement paths, native icon/header presentation and the corresponding collection-index mapping; it is not a full indirect writer or scene-resource closure.

The four logical tab roots initially registered by 0xf9ac0 are not a universal final gameplay count. Later original routine 0x107690 constructs a new ordered list and replaces the crafting widget's tab roots through 0x280440 at 0x108177. For current actor byte +0x14c values one through four, that completed replacement has six logical roots: two selected by the byte followed by four common roots. For other byte values, the inspected routine supplies only the four common roots. It does not retain two empty prefix slots for an unrecognized value. These statements describe the actual completed branches, not a guarantee that every class-byte mutation immediately invokes replacement.

The crafting widget is Game+0x340, equivalently interface+0x228 because the interface begins at Game+0x118. Constructor 0x27c950 initializes its tab-root linked-list sentinel at widget+0x260, eight-byte element count at +0x268 and selected tab at +0x2b4. The list is initially empty. Mode argument two is stored at widget+0x280; it is not a control count. The initial 0xf9ac0 registration clears a temporary list at 0xff2cf, appends four successive tab-template clones and registers them at 0xff363. That initial interval alone establishes four roots and their construction order, without the class-specific prefix or the later common icon assignments described here.

The complete direct-call inventory present in the supplied calls.csv and confirmed in original assembly for target 0x280440 has four sites. Routine 0xf9ac0 calls it at 0xff189 on the mode-zero inventory widget at Game+0x330, at 0xff363 on the mode-two crafting widget at Game+0x340 and at 0xff8c2 on the mode-three shop widget at Game+0x350. Routine 0x107690 calls it at 0x108177 on interface+0x228, the same crafting widget. No additional direct call or direct tail-jump to that target appears in the inspected original assembly listing. This is an inventory of those records/listed direct instructions, not proof that arbitrary indirect calls or aliased writes cannot exist.

Routine 0x107690 receives the interface in RCX. It reads Game through interface+0x5c0, World through Game+8 and current actor through World+0x448, then inspects the actor's single byte +0x14c. It creates a fresh temporary linked list and clones the native tab template through 0x3308e0 for each chosen root. Every root is appended at the list's back, either through the inspected explicit append sequence or equivalent helper 0x101990. Hence its forward order is the construction order. The routine reads the class-selection byte once for this branch choice; it does not derive a per-control group-remapping table from recipe contents.

For byte value one, the first two roots use native resource identifiers craft-warrior-weapons and craft-warrior-armor. Value two uses craft-ranger-weapons and craft-ranger-armor; value three uses craft-mage-weapons and craft-mage-armor; value four uses craft-rogue-weapons and craft-rogue-armor. Each recognized branch then reaches the same common append interval, whose four resource identifiers are craft-jewels, craft-cooking, craft-alchemy and craft-ingredients, in that order. These are literal original resource identifiers. They are not inferred names for undocumented item categories or an assertion about resource images absent from this evidence.

For recognized values one through four, the resulting ordinal-to-icon order is therefore zero for the selected weapons identifier, one for the selected armor identifier, two for craft-jewels, three for craft-cooking, four for craft-alchemy and five for craft-ingredients. For other values, the four common roots instead occupy ordinals zero through three. That exceptional sequence has no hidden offset of two in the inspected routine. The ordinary recognized-class conclusion must not be silently generalized to those other byte values.

The icon assignment is concrete scene work, not merely storage of an icon name in the tab-list node. For each new root 0x107690 calls 0x102930 with the cloned tab scene, the child name background and the chosen resource identifier. That helper resolves the target background and resolves the named resource from interface+0x328. When both are found, it removes an existing icon child if present, clones/attaches the resource into the target, names the new child icon and adjusts its presentation transforms. If lookup fails, the helper returns without installing that icon. The surrounding 0x107690 append still occurs; an absent icon is not itself a removal of that logical root from the tab list. Actual asset pixels and all resource lookup outcomes are outside this contract.

The replacement is list assignment, not accumulation of the old four roots followed by six more. Routine 0x280440 assigns the supplied list into widget+0x260 through 0x27c540. That assignment overwrites existing node payload pointers in order, appends nodes if the replacement is longer and unlinks/frees surplus destination list nodes if it is shorter. Thus a completed four-to-six replacement has count six, and a later six-to-six replacement does not grow the logical count to twelve. The stored node payloads are scene/control pointers, not inline scene objects or recipe records. Only 0x280440 is recorded as the direct caller of this assignment helper in the supplied call records.

After assigning the pointers, 0x280440 removes the old tab-area children through 0x330a80, then attaches the new roots to widget+0x218 in supplied order through 0x32f640. Original removal 0x33dda0 recursively removes scene children, detaches the old scene, updates relevant UI capture/hover references and invokes its deleting virtual entry; a narrowly scoped UI+0x90 critical section protects one removal-list operation. The replacement then lays out the roots and installs callback 0x27f980 with the same inventory-widget receiver on each logical root and propagated subordinate widgets. The temporary source list is destroyed through 0xcc140 after registration; that cleanup frees temporary list nodes/sentinel, not the newly attached scene pointers. Old root or subordinate-widget addresses must not be presumed live across this replacement merely because some destination list-node addresses were reused. The entire replacement is not established as an atomic publication by that one internal critical section.

There are three directly recorded callers of 0x107690, independently confirmed in assembly. Game constructor 0x7ea80 calls it at 0x7f739 after the successful saved-character-selection branch has loaded the selected actor through 0x9bb20 and performed the adjacent world/setup work, then calls crafting rebuild 0xb2180 at 0x7f74d. This branch occurs after initial interface creation, so it is a concrete constructor-time replacement of the earlier four-root registration. If that saved-selection branch is not taken, this call is not established merely by reaching the initial UI constructor.

Character-selection routine 0x9f7c0 calls 0x107690 at 0x9f926 in its valid existing-character branch, after loading the chosen character through 0x9bb20, then calls 0xb2180 at 0x9f93a. That routine holds the World+0x3c8 critical section through this branch, from its entry call to 0x2abb70 until its normal ending 0x2b9890. Its separate invalid/new-character branch initializes the creation actor, sets actor byte +0x14c to one and runs creation-preview setup including 0x272950 and 0x272d90. The inspected new-character branch does not take the existing-character branch's 0x107690 call. Consequently opening the creation preview is not independently proof that the initial four crafting roots have already been replaced with six.

New-character completion routine 0x9ea10 calls 0x107690 at 0x9efa5 after its actor/name/character-list work and interface refresh 0x107440, then calls 0xb2180 at 0x9efb9. Original UI setup 0xf9ac0 binds 0x9f7c0 to a control displaying the literal Select text and binds 0x9ea10 to the corresponding creation-completion control. These callers establish ordinary selection/completion reachability without assuming that a nonnull actor means tab setup is finished. The earlier World lock pair inside 0x9ea10 ends before this later tab replacement call; it does not establish one continuous World guard for the whole completion routine.

Class-preview changes have a distinct update boundary. Routines 0x2723d0 and 0x272420 change the creation widget's four-byte selector at +0x244 with wraparound across zero through three and call 0x272d90. That preview updater writes current actor byte +0x14c from the selector plus one and updates preview state while holding its observed World guard. Its inspected body does not call 0x107690 or 0x280440 and does not write the crafting tab-root list. Therefore a preview class-byte change alone is not the same operation as replacing the crafting roots; the observed completion/selection callers later rebuild them from the then-current actor byte. A full census of other class-byte writers remains unproved.

The runtime collection mapping is direct ordinal indexing. Routine 0x103200 binds crafting widget+0x1e8 to Game+0x17a8, whose outer elements have stride 0x18. Draw 0x27d2b0 enumerates stored tab roots in forward order and writes the hovered root ordinal to widget+0x2b0 when its hit test succeeds. Callback 0x27f980 accepts that cached ordinal only when it is nonnegative, below the bound collection's actual outer-group count and different from selected tab +0x2b4; it then stores the same integer as selected tab. The inspected mode-two row/draw and selection paths index the bound group with that integer directly. No class-dependent permutation between recognized-class root ordinal zero through five and Game+0x17a8 group index zero through five is established in these paths.

For the recognized-class six-root state, the native selected-tab header text independently confirms the displayed names for those numeric indices. Draw 0x27d2b0 emits the literal Crafting prefix and then Weapons for zero, Armor for one, Amulets for two, Cooking for three, Alchemy for four and Ingredients for five. These are original presentation strings, not names inferred solely from the icon resource identifiers. In particular craft-jewels is the resource identifier while the header for index two says Amulets. The header is drawn from selected tab; 0x107690 does not assign those text strings into every root as independent group metadata. Draw also has a Repair string for selected index six and a Formulas fallback, but those branches do not prove that a seventh Repair root is registered.

Collection rebuild 0xb2180 supplies groups zero through five through six calls to 0xb2ee0. The filler directly indexes the group selected by its integer argument and resets that inner group's live end before filling. The rebuild then ensures the outer collection has at least seven elements and clears group six's live end in its inspected post-fill interval. It does not derive the outer-group count from the logical root count, and ensuring at least seven is not an unconditional truncation to exactly seven. Thus six registered roots and an independently indexed group six can coexist. The presence of a header string or outer group is not evidence of another logical tab control, and the initial four roots do not imply that the retained collection has only four groups.

Advance/retreat routines 0x27f830 and 0x2802f0 use widget+0x268 as their wraparound count. Consequently their ordinary recognized-class replacement range is zero through five after count six has been installed. The mouse tab callback instead validates against the bound collection's group count while consuming a hovered ordinal generated by draw. These are different bounds. Neither 0x107690 nor the inspected 0x280440 body resets selected tab, selected canonical group/row or the cached hover index; a replacement alone is not a universal invalid-selection repair or guarantee that previously cached indices were refreshed in the same call.

Within the scoped original evidence, established structural writers to this tab-root list are constructor initialization, the assignment reached through the four listed registration sites and ordinary widget destruction 0x27d170, which frees its list nodes/sentinel and clears the count. The fresh-list append operations inside 0x107690 write its temporary list until assignment; they are not independent append-in-place operations on widget+0x260. Draw changes hover/presentation, and ordinary crafting collection rebuild changes Game+0x17a8; neither inspected body directly appends tab roots. Generic list helpers, aliased pointers, indirect calls, other UI teardown paths and all concurrent mutations have not been closed into a whole-program writer proof.

A useful ordinary-state conclusion is therefore conditional and concrete: after successful existing-character selection, successful new-character completion or the constructor's successful saved-character branch has completed 0x107690 with actor byte one through four, the crafting widget holds six logical roots in the class-prefix/common-suffix order above. Before that replacement, after a branch that does not invoke it, or for an unrecognized actor byte, the four-root observation can still apply in the bounded ways described here. No universal final count for every title-menu/intermediate state, resource failure, exception or future writer follows. The note describes original lifecycle and mapping facts and prescribes no replacement implementation or thread policy.
