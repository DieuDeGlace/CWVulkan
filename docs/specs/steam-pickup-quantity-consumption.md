# Native pickup-notice quantity consumption

This bounded contract is FINAL / STABLE / HELD following author readback. Its supported image is cubeworld.original.exe.unpacked.exe, AMD64 PE32+, image base 0x140000000, 5,757,952 bytes, SHA-256 7AF18CB28C8BF848F355287428C6390B2EA2A682CA466190F5EB9859C5D6F244. Evidence is restricted to the original binary, original function and longer-budget frame decompilations, assembly.txt and calls.csv after the standalone author rules. No other project prose, replacement implementation, SDK, tests, probes, captures or implementation history supplied evidence. Addresses below are RVAs. The scope is the identified notice representation, ordinary producer/transport and the receipt walk in frame 0xa5a50; it is not every inventory transaction or event reader.

The established consuming interpretation of notice+0xa8 is a two-byte unsigned quantity. At each observed quantity load in this receipt walk, the native frame zero-extends the word into a 32-bit register. Thus 0x8000 reaches these consumers as 32768 and 0xffff as 65535, not as negative signed 16-bit values. This result comes from actual consuming instructions, not the decompiler's constructor parameter types or the fact that two bytes were copied.

Offsets in this note use the notice payload base unless explicitly stated otherwise. The World+0x110 list has nodes with two eight-byte links before the payload. Payload+0 is the eight-byte actor identifier, +8 begins the embedded item record, +0xa8 is the two-byte quantity, +0xb0, +0xb8 and +0xc0 are three eight-byte position components, and +0xc8 is a four-byte flags field. In frame's node-relative addressing, quantity is at node+0xb8 and flags are at node+0xd8. Node+0xc8 is a position component, not the flags field. Confusing these bases would give the wrong width and meaning.

Copy constructor 0x3ac10 copies the actor identifier, the embedded item through 0x35400, exactly two quantity bytes, the three eight-byte components and four flags bytes. Its quantity load/store are at 0x3ac33 and 0x3ac3a; the flags transfer is at 0x3ac6b and 0x3ac76. A temporary zero extension while copying a word does not by itself define later arithmetic. The ordinary node helper 0x36eb0 allocates through 0x3c3b0 and constructs the payload at node+0x10; the node allocation is 0xe0 bytes.

For a complete input record, parser 0x39af0 transfers a raw 0xd0-byte notice representation into temporary storage before constructing a list node. Writer 0xf0f10 writes a four-byte list length followed by 0xd0 bytes per notice. The complete quantity word and complete four-byte flags field travel in this representation; neither routine establishes signed quantity arithmetic, clamps the quantity or reduces the flags field to the low byte. The representation also includes intervening and trailing padding. Quantity occupies only +0xa8 through +0xa9, and flags only +0xc8 through +0xcb; raw transport of the surrounding bytes is not a promise that constructor padding was initialized. Malformed/truncated-input behavior and a universal parser-validation contract are outside this note.

An ordinary ground-pickup producer is the reached branch in 0x2c3710 that appends through 0x36eb0 at 0x2c3ebc. The source ground record is a different representation. Its quantity is a word at ground-record+0xd4, copied into the notice quantity at instructions 0x2c3e62 and 0x2c3e69. Its flags are one byte at ground-record+0xc4. At 0x2c3e8e, that byte is sign-extended to a 32-bit integer, and at 0x2c3e95 the full result is stored in the notice's flags slot. Therefore the ordinary producer is not a zero extension of an eight-bit unsigned flag value into a four-byte field. For illustration of that instruction behavior, an input byte 0x80 would produce flags bits 0xffffff80; this does not assert that an ordinary ground writer actually supplies that byte value.

That producer also tests ground-record flag bit 0x02 at 0x2c3ef8. Its shown unset-bit branch resets the source record through 0x837e0; the set-bit branch skips that reset. Physical removal from the containing vector is not established by this branch. This is distinct from saying that ground flags and notice flags have the same storage width or a completely authenticated flag taxonomy. Other bits and every producer's possible flag combinations remain unqualified.

The frame receipt traversal begins at 0xaa608 by loading the current World's list at +0x110. It resolves the actor identifier through 0xe720. A failed lookup skips the notice. It converts or copies the notice's embedded item into temporary item storage through 0x10a720 at 0xaa647. The inventory and value tests described below use this resulting item. A source category of 0x1e can therefore be converted before these tests; treating every test as a test of the original embedded item is not established.

Only notices whose resolved actor equals World+0x448 enter the observed local inventory/counter mutation branches. For that local actor, the flags consumer at 0xaa65d tests bit 0x02 of the low byte at node+0xd8. If set, it derives a three-component position key, looks in the actor's separately allocated state collection at actor+0x1528 followed by +0x88, and skips the notice when the key is already present. Otherwise it inserts the key before continuing. This is the actual bounded meaning of the flag test here. No arithmetic or sign test of the entire flags dword is observed in this walk, and other flag bits are not assigned meanings. Remote-actor notices bypass these local inventory/counter branches and can still reach receipt presentation.

The first direct quantity arithmetic branch uses a resulting item with category byte 0x0c and subtype byte 0x0d at item+0x1c. It obtains a 32-bit counter from the actor's state collection at +0xf8, keyed using the current actor's two four-byte region coordinates at +0x150 and +0x154. Helper 0x83b20 returns the mapped value address at its node+0x24. At 0xaa77b, the notice word is zero-extended into a 32-bit value; at 0xaa782, it is added to the existing four-byte counter. The retained sum is the low 32 bits. There is no signed-word extension, 64-bit accumulation, multiplication or saturating clamp at this update.

The alternative ordinary-item path calls inventory insertion 0x4e810 at 0xaa7c5. Its Windows x64 inputs there are RCX pointing to actor+0x9f0, RDX pointing to the resulting item, R8D containing the zero-extended notice word loaded at 0xaa7ab, and R9D equal to 0xffffffff for default destination selection. That fourth argument is not notice flags. The callee consumes its quantity as a 32-bit integer, but the notice path supplies only values 0 through 65535. A notice word 0xffff cannot activate the callee's separate 32-bit quantity-equals-minus-one handling. A zero quantity returns at the callee's initial quantity test.

Inventory insertion retains four-byte counts. Existing stack updates add the supplied quantity with a four-byte operation, including the update at 0x4ea15. New stack entries store the 32-bit quantity beside the copied item in records of stride 0xa4. There is no conversion of the notice word to a signed 16-bit count on either route. Other callers may supply negative 32-bit arguments, including the distinct minus-one case, but their behavior is not evidence that the receipt word is signed.

Two insertion branches are direct scalar counter updates rather than ordinary item-stack storage. Resulting item category 0x0c with subtype 0x0b adds the quantity to inventory-base+0xbc at 0x4e89e. Since this inventory base is actor+0x9f0, that destination is actor+0xaac. Category 0x0e adds it to inventory-base+0xc0 at 0x4e8ae, hence actor+0xab0. Both additions retain the low 32 bits. The second counter's complete semantic name is not established here.

Actor+0xaac is authenticated as the gold-related counter by the same frame's later reporting code, which snapshots it, detects an increase and appends the original literal " GOLD" to the displayed difference. There is also a separate item-value route to that counter. At 0xaa78d the frame calls 0x109070 with the resulting item alone. If the result is nonzero, it calls that helper again at 0xaa79d and adds its 32-bit result once to actor+0xaac at 0xaa7a2. If the result is zero, it takes the inventory-insertion path instead. The helper tests for resulting item category 0x1f; it does not receive the notice quantity.

No multiplication of notice quantity by item-derived gold value occurs in these audited receipt branches. The direct-quantity gold form adds the zero-extended quantity through 0x4e810; the item-value form adds the helper result once. In particular, a zero quantity does not itself prevent the latter branch from computing and adding a nonzero item-derived value, subject to the earlier actor/flag gates. The value helper contains its own integer and floating-point arithmetic, which must not be confused with quantity scaling. Its integer seed manipulation uses 32-bit operations; an unsigned multiply at 0x1090a1 supplies a high half used by its remainder calculation, so treating every internal multiply as an isolated low-32-bit product would be incorrect. Its final multiplication at 0x1090d7 is binary32 floating point, followed by truncating conversion to a 32-bit integer at 0x1090df. This note does not reproduce the complete item-value formula or qualify unrelated transaction products.

The gold counter additions themselves are four-byte machine additions: their stored results wrap modulo 2 to the power 32, with no saturation established. The frame's earlier snapshot is read at 0xa6ffb. The later gold-gain decision reads the current counter at 0xad0f1 and makes a signed 32-bit comparison at 0xad103, skipping the report when the current value is not greater. When it reports, the difference is formed by a four-byte subtraction at 0xad22e, again retaining only 32 bits before integer formatting. Widening first or applying an unsigned-increase rule would change this observed behavior. Overflow can therefore affect whether a gain is reported and the signed displayed difference; the report is not an unbounded total.

The third observed quantity load is at 0xaad94, again zero-extending the word into R8D. At 0xaada9 the frame calls presentation routine 0x9d6f0 with Game in RCX, the resulting item in RDX, this 32-bit quantity in R8D and the resolved actor pointer in R9. R9 is not the flags field. The formatter has 32-bit integer-count formatting and a positive-count condition on some text routes. These notice values remain nonnegative there, including words with their top bit set. The formatter is not evidence of an additional inventory or gold multiplication.

The receipt walk occurs within the observed frame's caller-held World+0x3c8 critical-section interval, entered through 0x2abb70 at 0xa6464 and released through 0x2b9890 at 0xadb23. This qualifies that caller scope, not every writer, parser, inventory caller or external observer. Conversion, insertion and presentation can allocate or invoke runtime/UI work; the later gold-gain presentation also performs random draws. A full transitive mutation/RNG census, universal exception rollback and a universal queue-lifetime guarantee are not established. No replacement-engine arithmetic policy, capture rule or synchronization prescription follows from this note.
