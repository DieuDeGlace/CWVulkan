# Native inventory tab callback registration and dispatch

This bounded contract is FINAL / STABLE / HELD following author readback. The supported image is cubeworld.original.exe.unpacked.exe, AMD64 PE32+, image base 0x140000000, 5,757,952 bytes, SHA-256 7AF18CB28C8BF848F355287428C6390B2EA2A682CA466190F5EB9859C5D6F244. Evidence is restricted to that original binary, original function decompilations, assembly.txt and calls.csv after the standalone author policy. No other project prose or implementation material supplied evidence. All addresses below are RVAs. The scope is registration 0x280440, its concrete callback binding and direct input-dispatch path, the inspected Windows callers and the crafting registration sequence in 0xf9ac0. It is not a complete virtual override, event emitter, control-state writer or input-mode census.

The registered direct route for callback 0x27f980 is left-button down. The numeric event-map key installed by 0x280440 is two, and the concrete left-down dispatcher 0x340ec0 looks up that key and can synchronously invoke it. Its ordinary Windows route runs inside Game mouse handler 0x94900's call to interface dispatcher 0x101020. The inspected left-up dispatcher instead directly looks up event-map key three. These numeric event-map keys are distinct from Windows message numbers and from the Game handler's button indices. In particular event key two is not evidence that a callback is a middle-button event or a release event.

Registration 0x280440 receives the inventory widget in RCX and a temporary linked list of tab scene/control pointers in RDX. It copies that ordered list into widget+0x260 through 0x27c540. Widget+0x260 is the sentinel pointer and +0x268 is the eight-byte logical element count; this stored tab-control collection is a linked list, not a vector whose length comes from pointer subtraction. The list nodes contain their scene/control pointer at +0x10. The helper processes the supplied tab controls in forward list order, attaches them to the tab-area scene at widget+0x218 and places them sequentially. It then registers the same inventory callback receiver for each supplied tab control's widget reached at scene+0x70.

Assembly at 0x280633 through 0x28064e establishes the binding arguments independently of symbolic event names. The binding helper 0x27c790 receives event key two, the inventory widget as receiver and a copied member-call descriptor naming 0x27f980 with zero receiver adjustment. Both trailing byte flags are one. The first requests propagation to subordinate widgets; the second is stored as the listener's enabled-state requirement. A control's ordinal is not embedded as a separate callback argument. The same receiver and callback are installed for each logical tab root.

Routine 0x27c790 stores listeners in the target widget's tree at +0x188, keyed by four-byte integer event values. The value is a pointer to a separately allocated 0x28-byte binding; a replaced nonzero old binding is freed. The binding has its invocation vtable at +0, the enabled-state requirement byte at +8, receiver pointer at +0x10 and member-call descriptor at +0x18. Original image vtable RVA 0x46f228 points to callable invoker 0x288c40. That invoker applies the descriptor's signed receiver adjustment and transfers to its stored code target. For the descriptor installed here, that resolves to 0x27f980 with the inventory widget in RCX. The receiver is borrowed; this binding operation is not ownership of the inventory widget.

Propagation uses 0x32ac80 and 0x32aba0 to collect subordinate widgets and recursively installs the same event binding through 0x27c790. The inspected collector skips scene branches having flag bit two set at scene+0x80 and descends through scenes without their own intervening widget. Therefore the count of four logical crafting tab roots established below is not necessarily the total number of listener allocations across every template descendant. The complete resource-defined subtree and all later replacements are not established here. Clone helper 0x3308e0 ordinarily sets a cloned scene's event-target pointer at +0x78 to its cloned widget at +0x70 when the prototype has a widget, and otherwise can inherit the parent's event target. This and propagated bindings explain how a hit on a subordinate scene can reach the same inventory callback receiver without passing a tab ordinal as an argument.

The concrete window-message procedure 0x133c70 treats message 0x201 as the left-down path: it calls SetCapture and then 0x94900 with Game and button index zero. Message 0x202 calls ReleaseCapture and 0x965e0 with button index zero. The same procedure maps 0x204/0x205 to index one down/up and 0x207/0x208 to index two down/up. These are the original numeric Windows-message branches; the left/right/middle descriptions follow their concrete message values and observed down/up handler pairings. The SetCapture/ReleaseCapture calls concern Windows capture. They are not writes to the separate UI capture slot discussed below.

At callsite 0x94953, Game handler 0x94900 passes the interface at Game+0x118 to 0x101020 while preserving the button index. This call occurs before the handler's later crafting selection/recipe branch. Interface+0x5c0 supplies Game, and Game+0x20 supplies the UI owner. For index zero, 0x101020 tail-transfers to 0x340ec0 at 0x101114. No wait for the corresponding Windows release is part of this call chain. The installed tab binding can therefore execute and change selected tab before 0x94900 continues after 0x101020 returns.

The left-down UI dispatcher first sets bit zero of the four-byte button-state value at UI+0x1a8. It chooses the scene in UI+0x168 when that slot is nonzero; otherwise it performs hit testing through 0x333f60 from UI root +0x140 using the stored pointer coordinates at +0x180/+0x184. Setter 0x33c410 directly writes the UI+0x168 slot, establishing its distinct internal capture role. Hit testing itself has active-state, scene-flag, geometry and subtree-order conditions; a Windows down message does not by itself establish that any particular tab is the target.

For a selected scene, the down dispatcher uses its event-target widget pointer at scene+0x78. If that widget is nonnull and enabled at widget+0x1a0, it first calls virtual slot +0x58. The direct listener lookup then requires scene flag bit one at scene+0x80 to be clear, a nonnull event-target widget and a nonnull listener returned by 0x32a210 for key two. The listener is invoked if the target widget is enabled or the listener's enabled-state requirement byte is zero. Because 0x280440 installs that byte as one, this registered path requires an enabled target. Widget+0x1a0 is not a remembered mouse-pressed byte: base constructor 0x328ff0 initializes it to one, clone 0x329210 copies it and setter 0x32a8d0 changes it while issuing native widget:enable or widget:disable state changes.

Original assembly fixes the down call boundary precisely: key-two lookup is at 0x341016 and binding invocation at 0x341035. Those operations invoke the binding synchronously on the current call stack when their gates pass. Setting UI button-state bit zero is not accompanied by a local requirement that its previous value was clear. A release or completed click cycle is therefore not an independently required prerequisite of this dispatcher route. The tab callback may still return without a selection change because of its own state checks.

Additional down work is separate from that direct listener path. If the chosen event-target widget has bit five set at widget+0x150 and is enabled, the dispatcher remembers it in UI+0x1b0 and traverses the root with the visitor at 0x33aac4, which forwards virtual slot +0xe0. Otherwise it clears that remembered slot. The dispatcher also handles its prior-widget slot +0x170 and can emit numeric event 0x13 through 0x342560. Neither the bit-five visitor path nor a nonzero UI+0x1b0 is a prerequisite to the later key-two lookup. Finally it traverses active scene branches with visitor 0x33aad0, forwarding virtual slot +0xe8. These visitor calls are not themselves evidence that a numeric key-two listener was selected.

The shared traversal 0x33c360 requires the scene's active state value to be nonzero and scene flag bits two and one at +0x80 to be clear. It forwards a visitor to a nonnull widget at scene+0x70 and then recursively processes children in forward list order. The corresponding ordinary base widget virtual entries +0xe0/+0xe8/+0xf0 resolve to the return-only entry 0xe8a20 in the original base vtable at 0x477988; derived override behavior is not exhaustively audited. The proof of this tab callback's left-down route is the explicit map lookup and binding invocation, independent of such visitors. It does not require treating all virtual visitors as harmless or identifying a numeric event tag from a vtable offset.

The left-up path is separately concrete. Game handler 0x965e0 calls interface routine 0x101120 at 0x96767, and button index zero tail-transfers to 0x3410e0 at 0x101159. That dispatcher clears bit zero of UI+0x1a8, chooses the internal capture scene or hit-test result, calls the enabled event target's virtual slot +0x60 and directly looks up key three at 0x34117b before binding invocation at 0x34119a. It can additionally issue key 0x0e when the selected and current hit event targets differ and later uses visitor 0x33aadc for virtual slot +0xf0. It does not perform the key-two lookup used for the tab registration in its inspected direct listener branch. Thus the installed binding is authenticated as a down binding, not a left-up binding. Arbitrary derived visitor/virtual implementations, manually emitted event keys, replacement bindings and a complete indirect release-call closure remain unqualified.

Other inspected dispatchers reinforce the distinct number spaces. Interface button index one selects down dispatcher 0x3415f0, which directly looks up event key five. Index two selects down dispatcher 0x341300, which directly looks up event key eight. Pointer movement 0x3418d0 directly considers event keys 0x0d, 0x0e and 0x0c for its respective target-transition/movement work. Generic emitter 0x342560 accepts an explicit event key and invokes a matching listener subject to the target/listener gates. A complete census of every call that could explicitly emit key two is outside this bounded audit.

There are additional non-message callers of the Game down/up handlers. The ordinary input loop 0x1355a0 contains polled-input branches that call 0x94900 and 0x965e0 with indices zero, one or two when corresponding stored input bits change. These are not independently Windows 0x201/0x202 deliveries. The original direct-call records include left-down sites 0x1372d6 and 0x1374ae, with surrounding native transition and input-mode gates. They converge on the same Game/interface/UI down path once called. This audit does not name every polled input mode or certify complete de-duplication between input sources.

The crafting registration count is independently established from the exact initialization interval in 0xf9ac0. Constructor 0x27c950 is called at 0xff25b with mode argument two; the resulting widget is stored at interface+0x228, which is Game+0x340. The temporary tab list is cleared through 0x3c9c0 at 0xff2cf, so earlier inventory-tab entries are not carried into this registration. Four sequential clones of the native tab template follow, through 0x3308e0 at 0xff2dd, 0xff2fe, 0xff31f and 0xff340. They are appended by 0x101920 at 0xff2f0, 0xff311, 0xff332 and 0xff353, respectively. That helper appends at the list's back; the resulting forward order is exactly the four-clone construction order, with logical ordinals zero through three. Original binary string RVA 0x4414d8 names this template tab.

The single crafting call to 0x280440 at 0xff363 receives that four-element list and the widget at interface+0x228. Its ordinary successful registration therefore establishes four logical tab controls in the stored list, count four at widget+0x268, with the callback registration traversing them in that same order. Constructor mode argument two is stored at widget+0x280; it is not the number of registered tabs. The constructor itself initializes an empty tab-control list through 0x86fc0 and supplies no list of four controls. The constructor's other resource/pointer arguments likewise do not establish the later list length. The four controls do not by themselves establish a four-group bound for the separately bound item collection, and a logical-root count is not an exhaustive descendant-listener count.

Callback 0x27f980 takes the inventory widget as its sole established receiver and reads cached hovered-tab integer +0x2b0. It requires a nonnull bound collection, a nonnegative hovered index below that collection's actual outer-group count and an index different from selected tab +0x2b4 before changing selection. The inspected list draw 0x27d2b0 writes +0x2b0 from the ordinal of a tab control whose hit-test succeeds. The callback does not recover the clicked tab ordinal from a unique per-tab argument. Therefore actual callback execution, hovered-tab freshness, target-hit identity and a successful selected-tab change are separate facts; the binding alone does not guarantee that each dispatch changes the tab. All other writers, capture changes, resource overrides, enabled-state transitions, exception behavior and synchronization remain explicit limits. No replacement implementation or universal event/thread policy is prescribed.
