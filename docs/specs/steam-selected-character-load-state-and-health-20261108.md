# Selected character loading, decoded state, and health

This is an independent, code-free original-side contract for the selected character-load route, its reader, the ordinary Continue and Select branches, and the bounded reset/rebuild and later-update distinctions described below. All addresses are RVAs in the supported x64 Steam image.

The supported file is binary/cubeworld.original.exe.unpacked.exe beneath C:/Users/DieuDeGlace/Documents/decompiled cube world steam. Its SHA256 is 7AF18CB28C8BF848F355287428C6390B2EA2A682CA466190F5EB9859C5D6F244; Machine is 0x8664, image base 0x140000000, and PE timestamp 0x5D93AB0D. These values were checked against the file and the original export metadata. Twenty-six selected instruction sites, including the raw health store, orientation zeroing, extra scalar stores, inventory aggregate stores, gold comparison, buff replacement, and separate health recomputation/rescaling stores, were compared with the corresponding file-backed bytes and matched.

Only the standalone source-author policy and filename-selected original executable, native listings, decompiled routines and original metadata were inspected. No replacement implementation, exporter, project startup/memory/history, tests, SDK/dependency source, owner outputs/captures, or earlier held handoff was read. Earlier held artifacts were not changed. This document gives no implementation guidance.

For compact field descriptions, E is the destination entity; D is the CharacterData object addressed by E+0x1528; G is Game; W is the viewed World at G+8. A locally selected destination is W+0x448. Offsets name operands, not an exhaustive class layout or an inferred gameplay purpose.

## Load admission and ownership

RVA 0x9BB20 takes Game, a signed four-byte record index, and a destination entity. It enters the viewed World protection scope through 0x2ABB70, forms the index's decimal narrow-string key, and enters the critical section at G+0x1C98 before the database lookup on G+0x2268 through 0x670F0. A nonzero lookup result admits the buffer transformation at 0x66D10, wrapper initialization at 0x147750, and character decoding at 0x147800. The native call at 0x9BCDA explicitly passes the destination as its second argument; this operand is missing from the decompiler's displayed call.

A missing database entry skips both decoding and the subsequent fixed-item insertion. In particular, missing lookup does not run the entity reset and does not replace D. There is no displayed success result used by Continue or Select to prevent their following UI work. Decoding takes place while both protection scopes remain held. Normal completion leaves G+0x1C98 before leaving the World scope, then destroys the temporary buffers and stream objects. This establishes call order and protection operands, not a universal exclusion guarantee for every other writer.

The inspected static call metadata identifies 0x9BB20 calls in Game construction at 0x7F488 for roster entities and 0x7F71A for the selected local entity, Continue at 0x966B4, valid Select at 0x9F856, and roster reload at 0x9FE40 inside 0x9FDF0. These are bounded discovered calls, not a census of every possible indirect or undiscovered route. Roster entities are separate destinations; their reads must not automatically be attributed to W+0x448.

## Reset and defaults precede record decoding

The first entity operation in 0x147800 is 0x64A90 at 0x14784B. Its reached core reset, 0x64C00 on E+0x10, clears numerous motion/action/relationship fields, equipment, name storage, class/specification bytes, and home coordinates; it sets level to 1 and experience to 0. The outer reset destroys the existing inventory contents and clears the old buff list at E+0x980, making its count at E+0x988 zero and freeing its nodes. This initial clear precedes every saved buff read.

The reader then destroys any old D, allocates a new 0x300-byte D and initializes it with 0x7FF20. It prepares empty equipment and assigns it to E+0x278. Next it assigns an empty inventory aggregate with 0x83540 at 0x147915, temporarily sizes the inventory outer container to six entries, constructs a default core with 0x4D600, copies that core to E+0x10 with 0x3B7A0 at 0x147984, and writes the one-byte E+0x60 value to zero.

The inventory aggregate assignment is not only a move of the three outer-vector pointers. Relative to its E+0x9F0 receiver, 0x83540 also copies a four-byte value at +0x18, the item at +0x1C through 0x9CD0, and four-byte values at +0xBC and +0xC0. Thus the reader's empty temporary resets E+0xA08 to zero, makes the cursor item at E+0xA0C empty, and zeroes E+0xAAC and E+0xAB0 before their saved values are read. Native stores at 0x83588, 0x83596 and 0x835A7 confirm these relative destinations. The item copy covers its defined fields, including the 128-byte component area and byte +0x9D; this is not a promise to zero every padding byte.

The default core at this point supplies zero position/orientation, health bits 0x43FA0000 (single-precision 500), level 1, experience 0, class/specification zero, an empty name, and the eight-byte home pair consisting of two -1 values. These are reset/default values before a successful field read, not post-read normalization of decoded health.

Entity construction at 0x4CE80 also uses 0x4D600, constructs an empty buff list, initializes the inventory/cursor aggregate and both four-byte +0xAAC/+0xAB0 fields to zero, and initializes the unaligned eight bytes at E+0x9A4 to 0x000000003F800000: +0x9A4 is 0x3F800000 and +0x9A8 is zero. The reader's core copy and the examined 0x64A90/0x64C00 reset do not themselves reset +0x9A4/+0x9A8. Complete saved records overwrite them later; absent reads must not be assumed to recreate their constructor values.

## Record order and directly decoded values

The reader first consumes a four-byte record word into wrapper+0xC. Later branches compare this word with 9 and 4; it is not an up-front acceptance test for a complete record. The following order is directly visible in 0x147800:

1. Twenty-four position bytes are copied to E+0x10, +0x18 and +0x20. These are three eight-byte slots, with no home-based placement or coordinate scaling at this read.
2. Twelve bytes are consumed into E+0x28 through +0x33, then E+0x28 is unconditionally cleared with an eight-byte store and E+0x30 with a four-byte store at 0x147A37 and 0x147A3B. The saved three four-byte orientation slots are therefore consumed and discarded.
3. Health is copied as four raw bytes to E+0x180 at 0x147A68. It is followed by four-byte level at +0x144, four-byte experience at +0x148, one-byte class at +0x14C, one-byte specification at +0x14D, and the four-byte values at +0x9A4 and +0x9A8. The respective native stores are 0x147A9B, 0x147ACE, 0x147B02, 0x147B35, 0x147B67 and 0x147B9A.
4. Eleven 160-byte equipment records are read through 0x1496D0, in destination order +0x278, +0x318, +0x3B8, +0x458, +0x4F8, +0x598, +0x638, +0x6D8, +0x778, +0x818 and +0x8B8.
5. A four-byte name length precedes the bytes copied to E+0x958, followed by an explicit zero byte at E+0x958 plus that length. No character-case, content or sixteen-byte length normalization is visible in this path.
6. The reader destroys the first newly constructed D and creates another fresh 0x300-byte D with 0x7FF20. It reads its first twenty bytes, then reaches appearance reconstruction at 0x53E80 with E+0x64, E+0x78 and D. The selected routine's entity-derived arguments concern the type/appearance area; this is not a call to the health-value routine 0x5FAC0.
7. A four-byte outer inventory count replaces the temporary six-entry size. Each outer entry is a 24-byte descriptor, with a four-byte inner count and count times 0xA4 bytes of inventory records. No cursor item/count is decoded here. The two following four-byte fields are stored at E+0xAAC and E+0xAB0.
8. D's item list at +0x18 is populated from a four-byte count followed by 160-byte entries. The conditional and unconditional D sections below follow it.
9. After those D sections, eight home bytes are copied to E+0x1D0 at 0x1489C7. A four-byte buff count then precedes the second explicit clear of E+0x980 at 0x148A0E, followed by its decoded records.
10. The remaining D+0xF8, +0x108, +0x118 and +0x138 sections are consumed before the reader's temporary string destruction and return.

The +0xAAC comparison deserves its exact operand widths. At 0x147EB4 the stored signed four-byte value is sign-extended to 64 bits, then compared as unsigned with 0x2540BE400, decimal 10,000,000,000. A strict unsigned greater-than result writes the four-byte constant 0x540BE400 at 0x147ECA. Consequently every negative signed 32-bit input triggers that store, while every nonnegative signed 32-bit input lies below the comparison constant. The stored replacement is decimal 1,410,065,408. This is not a demonstrated 64-bit gold field or a conventional ten-billion cap on a 64-bit balance. The neighboring +0xAB0 four-byte field is read separately.

For a complete admitted record, the health store performs no floating-point comparison or arithmetic. Zero and negative finite health bits are stored just as positive finite values are. The remainder of 0x147800 contains no second E+0x180 assignment, no call to 0x5FAC0, and no health maximum, minimum, positivity, percentage or class-based rescaling operation. Level, experience, class/specification and +0x9A4/+0x9A8 likewise have no displayed post-read clamp in this reader. This claim ends at the examined load/caller boundaries; subsequent ordinary updates have separate health writes.

## CharacterData and decoded buffs

D+0x18 is a list with an eight-byte count at +0x20. For a record word greater than 9, the reader additionally loads the sections at D+0x38, +0x48 and +0x58 as eight-byte entries; +0x88 and +0x98 as twelve-byte entries; +0xA8, +0xB8, +0xC8 and +0xD8 as eight-byte entries; and +0xE8 from twelve-byte records through the reached insertion helpers. Each section is preceded by a four-byte count. These conditional sections are not read when that greater-than-9 gate fails.

For a record word less than 4, a separate legacy section is consumed and discarded: per entry it advances over a four-byte part, reads a length and corresponding temporary string, advances over twenty-four bytes, and destroys the string. It does not publish that temporary string as E's name.

The subsequent common sections load D+0x2C8 as four bytes and D+0x2D0 as a length-prefixed string, then replace the D+0x28 collection from eight-byte entries. Home and buffs follow. After buffs, D+0xF8 consumes eight-byte keys and four-byte mapped values. D+0x108 consumes sixteen-byte records and appends them into groups selected by the second and third signed four-byte components divided by 4096 with truncation toward zero. D+0x118 consumes eight-byte entries. D+0x138 consumes an eight-byte group key and four-byte item count, then 160-byte items. At 0x148E47 the reached append helper 0xA17D0 receives the item filled by 0x1474C0; the items are not merely read into an unused temporary. This is a bounded read-order description, not a full semantic interpretation or a new comparator audit.

At the buff section, 0x3C9C0 first empties E+0x980 and frees its old nodes. For a positive signed count, the reader consumes twenty-four bytes per record and appends them through 0x4CCB0 at 0x148A86, incrementing the eight-byte count at E+0x988. Valid complete records therefore retain the decoded list, in record iteration order, through the rest of 0x147800. No expiration filtering, type filtering, duplicate rejection or later clear is visible in the remainder of that reader. The initial reset does not imply that the newly decoded list is thrown away.

After a normal reader return, 0x9BB20 prepares a fixed 160-byte item whose defined identifier operands include byte 0 equal to 1 and four-byte +4 equal to 7, with its other initialized fields zero. It tests for an equivalent existing item with 0x5F440, whose reached comparison is 0x4DF60. If absent, it appends the item to D+0x18 and increments D+0x20. This changes CharacterData after decoding; it is not an equipment, health or buff operation. No broader item label is assigned here.

That branch then writes selected-slot metadata to G+0x2268, reaches the class-dependent UI rebuild 0x107690, the native no-op guard target 0xE8A20, and the derived recipe/UI work 0xB2180, followed by Game camera scalar writes. The examined valid branch has no direct local health assignment, no second 0x64A90 call, no cursor repopulation from the saved record, and no direct buff clear after the reader. The directly inspected 0x2E0B50 clears and rebuilds D+0x128 groups from D+0xA8 using World queries; it is not a whole-entity reset and does not directly overwrite the listed health, pose, home, inventory or buff fields.

Continue's selected load at 0x966B4 is admitted when the indexed integer values of the selected objects beneath G+0x118 and G+0x120 are both nonzero, the supplied input integer is zero, and the action integer at G+0x128's object+0x1F0 equals 3. Its newly created local entity receives default name/position, a separate three-coordinate result at E+0x1B8 from 0x2D3DB0, orientation/motion clearing, level 1 and a 0x5FAC0-derived health assignment before selected-record loading. When the saved selected-slot metadata is present, 0x9BB20 at 0x7F71A overwrites that local entity from the record, followed by 0x2E0B50, fixed-item additions through 0x9AFB0, and UI rebuild work. The earlier default health or position is not an after-load repair. Valid selection and Continue do not derive their decoded position from home; their directly read saved position and home are separate state.

## New-character branch and placement

An index below zero or outside the roster size takes Select's other branch. It shows the G+0x170 root, calls 0x64A90, clears the first name byte, writes E+0x60 zero, clears the three orientation slots and selected motion slots, and writes level 1. The reached reset has already put experience and class/specification at zero and emptied the old buffs. It then assigns E+0x180 from 0x5FAC0 at 0x9FAAE before the following provisional equipment writes and class byte 1 assignment. This is a distinct write order from loading a saved character.

It obtains a pair from 0x2D1100 and stores it as the two four-byte home components. It places the eight-byte X slot from the signed four-byte calculation home-X times 16 plus 8, shifted left 16 after extension; Y comes from home-Y plus 2, times 16, likewise shifted. Z is first zero and then replaced by the integer conversion of the terrain-height query result multiplied in single precision by 65536, whose bits at original RVA 0x42E5F8 are 0x47800000. These placement operations occur in the invalid-index/new-character route, without a saved position read. They are not a universal world-entry transformation applied after every valid load.

This branch then destroys/replaces D, clears the name editor, and reaches 0x272950 and 0x272D90. The latter publishes the selected type/class and appearance components into E and D, reconstructs appearance, and unconditionally calls 0x913B0 at 0x27317D. That rebuild empties equipment and the inventory/cursor/gold aggregate, creates six inventory categories with explicitly resized inner categories, and fills class-dependent equipment and initial items. After those changes it recomputes and assigns E+0x180 again at 0x91BB3. Only afterward does it clear D+0x18 and reach 0x9AFB0 to add fixed item entries. This second assignment explains why the earlier provisional new-character health is not necessarily its final value. The examined new-character chain does not directly reset +0x9A4/+0x9A8 to their constructor values.

## Later health/reset operations and evidence boundaries

A claim that decoded health is left as read is valid at the decoder and examined synchronous saved-character branch boundaries, not for an arbitrary future frame. Ordinary viewed Game update 0xA5A50 obtains a 0x5FAC0 value at 0xA702F before its World substeps. After the substeps or their admission failure, it compares a newly obtained value with the earlier one. A difference admits the single-precision division of the new value by the earlier one, multiplication by E+0x180, and health store at 0xA7402, followed by an upper selection against a newly computed value and store at 0xA743E. There is no positive-old-value guard at this particular division. For ordered finite operands the latter selection keeps the smaller health/computed value; it supplies no lower bound that changes a negative result to zero. No claim about NaNs, infinities, zero divisors or all downstream effects is made from the finite-record facts.

A separate branch in that update, gated by global byte RVA 0x5514CF, replaces nonpositive health with a 0x5FAC0 result at 0xA9C79, and has additional action/flag-dependent target-position work. The writer and ordinary meaning of that global byte were not proved here; the branch must not be promoted to unconditional loading behavior.

The reached interaction routine 0x98180 has an explicitly displayed “Revive” label when local health is nonpositive. If its earlier admission guards pass and its input-edge condition is admitted, it reaches 0x65FB0, records the previous position in D+0x290/+0x298/+0x2A0, obtains another position through 0x2C2860, writes the three position slots, and finally assigns health from 0x5FAC0. The concrete 0x65FB0 reset clears/frees E+0x980 buffs. This is a later admitted interaction, separate from Select/Continue decoding. Its placement helper reads D+0xA8 and World state; this contract does not replace its untraced selection algorithm with an assumed home-placement rule.

World update 0x2DA6C0 also reaches 0x2E0DB0. That routine has conditional entity lookup/relationship/equipment work, including health rescaling and reset calls on selected receivers. Those are not an unconditional local-player post-load normalization. Concrete receiver membership, later relationship changes and concurrent network/gameplay writers cannot be inferred merely from the shared reset target. The decoded list may subsequently change under such independent gameplay/update routes; the specific load itself retains the list it just decoded.

The ordinary connection helper 0x3D820 was checked only to distinguish its client bookkeeping core reset from an E reset. Its 0x4D600/0x3B7A0 destination is client-object+0x78, not automatically W+0x448+0x10. Reusing a core-copy routine does not prove a local health or buff reset. Connection-time indirect effects and every alternate world-entry route are outside this contract.

Complete records mean the needed bytes, nonoverflowing representable counts/lengths, valid destination/container ownership, and normal helper returns are available along the selected format path. The reader repeatedly checks remaining bytes at each field; insufficient data generally moves the cursor to the buffer end and skips that particular store. It does not undo earlier resets or successful stores. Some loops use initialized defaults while other displayed local operands are not reliably initialized on failed reads. Name termination is written using the decoded length even if the name-byte copy is skipped, and no sixteen-byte destination-length bound is visible there. Count arithmetic, allocation failure, malformed strings, exceptions and abnormal returns therefore do not have an established transactional or safe fallback contract here.

A complete health-field read is different from an unread health field: the former preserves the supplied zero/negative/positive finite bits; the latter can leave the pre-read default 500. Unread +0x9A4/+0x9A8 can instead leave preexisting values because those fields are outside the default core reset. No finite-value validation, malformed-record recovery, exhaustive writer census, backend format integrity, thread interleaving guarantee or untraced reset side effect is inferred. The supported evidence is static original evidence, not a runtime capture.
