# Native crafting collection rebuild

This bounded original-evidence contract is FINAL / STABLE / HELD following author readback. The supported image is cubeworld.original.exe.unpacked.exe, AMD64 PE32+, image base 0x140000000, 5,757,952 bytes, SHA-256 7AF18CB28C8BF848F355287428C6390B2EA2A682CA466190F5EB9859C5D6F244. Evidence is the original binary, original native function and longer-budget frame decompilations, assembly.txt and calls.csv after the standalone author rules. No other project prose, implementation, SDK, tests, probes, captures or implementation history supplied evidence. All addresses below are RVAs. The scope is rebuild 0xb2180, filler 0xb2ee0 and the specifically identified storage, arithmetic, copy and caller edges; it is not the complete recipe-generation or crafting-action algorithm.

The retained collection is grouped item/count storage, not a vector of full recipes. The filler computes a signed 32-bit count using wrapped 32-bit carried totals and signed division. It starts with a minus-one candidate, treats any negative candidate as unset when considering another ingredient, explicitly makes the empty-ingredient result zero, and has no observed final general negative clamp before storing the count. The selected button separately receives a copy of a full recipe, including copied ingredient storage.

Rebuild 0xb2180 takes Game in RCX and obtains the current World through Game+8 and actor through World+0x448. Its outer guard compares the actor's inventory group-vector begin and end at actor+0x9f0 and +0x9f8. The test is for the existence of group headers, not for any nonzero carried item quantity. If there are no group headers, the shown rebuild body is skipped; it does not first empty all retained crafting rows or selected-button state.

The retained outer vector header begins at Game+0x17a8: begin, end and allocation-end pointers occupy +0x17a8, +0x17b0 and +0x17b8. Each outer element is a 0x18-byte inner vector header with begin/end/allocation-end at element+0, +8 and +0x10. Each live inner row has stride 0xa4, with a four-byte computed count at row+0 and an embedded item at row+4. This is the same count-before-item shape consumed by these inventory-like row helpers; it must not be confused with the ingredient record shape described below.

The ordinary rebuild calls 0xb2ee0 six times, in group-index order 0, 1, 2, 3, 4, 5, at 0xb29e0, 0xb29f2, 0xb2a04, 0xb2a15, 0xb2a27 and 0xb2a38. It then ensures the outer vector has at least seven elements and resets group 6's logical end to its begin. This does not force an already larger outer vector back to exactly seven elements, nor does it clear groups beyond 6 in the inspected body. Filler 0xb2ee0 similarly ensures that its requested group header exists and resets that group's end to its begin before filling it. Existing capacity can be reused; an empty logical group is not proof that its former backing bytes were erased or freed.

The filler receives the signed 32-bit group index in EDX and a temporary recipe-vector header in R8. Source recipes have stride 0xc0. Within a source recipe, the item begins at +0, a separate four-byte scalar is at +0xa0, and an ingredient-vector header occupies +0xa8, +0xb0 and +0xb8. An ingredient element has stride 0xa4, with its item beginning at element+0 and its four-byte required quantity/divisor at element+0xa0. In particular, the ingredient quantity is not at element+0, and the source recipe scalar at +0xa0 is not automatically the computed retained-row count.

Within the filler, there is one output row for each input recipe, in input traversal order. Zero or negative computed counts do not cause that row to be omitted. Duplicate input recipes are not deduplicated by this filler, and the count is not used as a sorting key. The row index used for selection therefore advances with the source recipe index. Rebuild constructs its temporary grouped inputs by appending accepted entries from the actor's known-recipe list in traversal order, followed by additional generated entries. The retained groups follow those temporary inputs and the six filler calls above. Complete human-readable group taxonomy, acceptance criteria and generated recipe contents are outside this bounded contract; no unsupported category names are assigned here.

For each ingredient, the filler visits the actor's carried inventory group headers and their 0xa4-byte rows. It compares the carried item at carried-row+4 against the ingredient item at ingredient+0 through 0x4df60. Each matching carried quantity is read from carried-row+0 as a four-byte value. Matching quantities contribute to a 32-bit accumulator; at 0xb3050 the native addition updates the low 32 bits. There is no 64-bit carried-quantity accumulation, signed-word interpretation or special handling of a carried minus-one quantity established at this sum. Negative stored counts and sums that wrap into a negative 32-bit interpretation consequently remain material to the later division.

At 0xb306e the wrapped accumulated bits are placed in the 32-bit dividend register. Sign extension at 0xb3071 supplies the high half required by signed division; it does not recover an unbounded or 64-bit accumulated total. At 0xb3072 the native instruction performs signed division by the four-byte value at ingredient+0xa0. The quotient truncates toward zero. This is not unsigned division and not mathematical floor division for negative inputs. No local pre-division guard establishes successful return for a zero divisor or the signed minimum divided by minus one. This note does not assert that ordinary recipe producers generate such values.

The candidate starts at signed minus one, visible at 0xb2feb. At 0xb3078 through 0xb3082, a negative current candidate is replaced by the next quotient; otherwise the smaller quotient is retained using a signed comparison. Thus minus one is the ordinary initial unset value, but the actual test treats every negative candidate as unset. For arbitrary negative or overflowed inputs, the retained result cannot be described simply as an order-independent minimum of all signed quotients. A negative result from an earlier ingredient may be replaced by a later nonnegative result. Ingredient order therefore remains relevant outside ordinary nonnegative arithmetic.

Empty ingredients are handled separately. The begin/end equality condition at 0xb3175 leads to the zero selection at 0xb3182. A recipe with no ingredient elements consequently receives retained count zero, not minus one or an unlimited-craft sentinel. For a nonempty ingredient span, no final sign-based zero clamp is present between the quotient/candidate handling and appending the row. A surviving negative candidate is stored as its four-byte result. This statement concerns the retained collection; independent rendering or later action rules are not qualified as part of this count calculation.

When appending, the filler stores that four-byte count and copies the recipe's item into row+4 through 0x35400. Growth uses 0x4e600 and can replace an inner row allocation. Outer growth uses 0x64f30 and can replace the outer allocation of group headers. Pointers to prior group headers or row storage are not assigned a stable lifetime by this rebuild. The item copy does not retain the source recipe-vector element address.

Selected-button updates are conditional on two four-byte comparisons. The filler compares its group index and current row index against the selection pair at the object reached through Game+0x340, offsets +0x278 and +0x27c. Only the matching recipe updates the button object reached through Game+0x348. The destination item is inline at button+0x1f8. The source recipe's four-byte +0xa0 scalar is copied to button+0x298. The ingredient vector is assigned to button+0x2a0 through 0x82f10 at 0xb332c. The selection pair is copied to button+0x2b8 and +0x2bc. The scalar copied to +0x298 is not the filler’s newly computed count merely because both are four bytes.

Helper 0x82f10 is a value-copy vector assignment. It can reuse destination capacity, allocate replacement destination storage, or set the destination's logical end to its begin for an empty source. Its reached copy helpers 0x6fbc0 and 0x7c360 copy ingredient items and their trailing four-byte requirements with stride 0xa4. The ordinary selected-button assignment therefore does not borrow the temporary recipe's ingredient-vector allocation. In 0xb2ee0 itself, a nonmatching selection does not execute this recipe copy or explicitly clear the button's prior recipe. Later generic UI update effects are not a complete selection-state census here.

The selected copy matters because the rebuild destroys the temporary full-recipe vectors on ordinary completion. Helper 0x6ff00 releases and clears their owned ingredient vectors, and the rebuild releases the temporary outer storage through the reached deallocation paths. Those temporary recipes are not the retained Game+0x17a8 rows. The selected button's copied ingredient allocation can outlive the temporary vectors. Complete button-destruction ABI, allocation-failure rollback and every later recipe writer remain outside this note.
