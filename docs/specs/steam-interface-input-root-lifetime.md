# Native interface input-root lifetime

This bounded contract is FINAL / STABLE / HELD following author readback. The supported image is cubeworld.original.exe.unpacked.exe, AMD64 PE32+, image base 0x140000000, 5,757,952 bytes, SHA-256 7AF18CB28C8BF848F355287428C6390B2EA2A682CA466190F5EB9859C5D6F244. Evidence consists solely of the original image, original native function decompilations, the longer-budget original frame decompilation, assembly.txt and calls.csv after the standalone author policy. No other project prose, implementation, SDK, tests, probes, captures or handoffs supplied evidence. Addresses below are RVAs. Scope is the supported ordinary startup, character-selection/completion, gameplay, Start Menu return and shutdown paths, together with the identified scene attachments and input gates. Graphics/device recovery, arbitrary indirect writers and full synchronization closure remain outside scope.

The inspected ordinary title and gameplay interfaces share one UI owner and one principal input root. Game+0x20 retains a pointer to the already constructed UI/graphics owner, and that owner's +0x140 contains the scene named root. Frontend branches, the gameplay branch and the independent options/controls panels are attached to that same root. They are separate scene branches and widget objects, not separately constructed input owners on each character transition. The observed transitions largely change active states, borrowed collection bindings and selected descendants; this does not mean every descendant control is permanent.

Startup routine 0x134cc0 allocates 0x5d8 bytes and constructs the owner through 0x38e100 at callsite 0x135121, publishing it in the original global at image RVA 0x551ac0. Constructor 0x38e100 first calls common UI-owner constructor 0x339b70 at 0x38e12a and then establishes the concrete graphics-owner state. The common constructor creates a scene named root through 0x33cd30 and stores its pointer at owner+0x140. It separately creates sources and fonts scenes at +0x148 and +0x150. Those latter roots have their own flags and are not evidence of a second input owner. A scene existing in the owner's registered-object storage is not, by that fact alone, a descendant of the input root.

At ordinary Game allocation, caller 0x1355a0 places that global owner pointer in the fifth argument to Game constructor 0x7ea80 at 0x136331. The Game constructor stores it at Game+0x20. It does not allocate a replacement owner there. The inline interface begins at Game+0x118; constructor 0xf8690 initializes that interface and stores a borrowed Game pointer at interface+0x5c0. Game constructor then creates the interface scenes and widgets through 0xf9ac0 at 0x7f4d4. These are different pointer roles: Game+0x20 is the owner pointer; the first pointer within the inline interface at Game+0x118 is a frontend scene pointer, not the principal owner or owner+0x140 root.

Scene construction 0x33cd30 accepts the owner and an optional parent. It creates an ordinary scene allocation of 0xc8 bytes with associated scene resources as needed and, when a parent is supplied, attaches the scene through 0x32f640. Scene+8 records its owner through the common object construction path, scene+0x40 is its parent and +0x48/+0x50 are its child-list header/count. A widget's associated scene is reached at widget+0x178. Native reparenting helper 0x3347f0 detaches the prior parent relation and attaches under the supplied nonzero new parent; a zero parent detaches. Cloning through 0x3308e0 or 0x333890 creates new descendant scenes in the source scene's owner and takes an explicit parent. These concrete edges support the relationships below without assuming that all pointers with similar offsets denote the same kind of object.

Routine 0xf9ac0 creates several frontend branch scenes directly under owner+0x140. The initial main/title branch is the first interface pointer at Game+0x118 and is initially active. The character-selection branch is interface+0x18, Game+0x130; character creation is interface+0x58, Game+0x170; the other inspected world-selection/creation branches are interface+0x80 and +0xe8, Game+0x198 and +0x200. These four later frontend branches initially have inactive state values. Their controls are children of these existing branch scenes: the Select control is cloned under the character-selection branch and invokes 0x9f7c0; Create Character is cloned under the character-creation branch and invokes 0x9ea10. Their owner arguments and ancestry lead to the same principal input root.

The gameplay container is interface+0x108, Game+0x220, also created under owner+0x140. The inventory, crafting and shop widgets at Game+0x330, +0x340 and +0x350 are constructed in 0xf9ac0 on scenes cloned under that gameplay container. Their constructors receive Game and obtain the same owner through Game+0x20. The inventory constructor's mode values zero, two and three select widget behavior; they do not select different owners or input roots. Their associated scenes are initially inactive. The system menu widget at Game+0x358 is constructed through 0x291c70 on another scene under the same gameplay container and is initially inactive. Its native draw 0x291e00 presents Options, Controls, Start Menu and Exit Game choices.

The options and controls panels take a different parent branch while retaining that same owner. In 0xf9ac0 the objects at interface+0x538/+0x540, Game+0x650/+0x658, are constructed through 0x287050 and 0x275a70 on scenes cloned directly under owner+0x140. Both are initially inactive. The options object is bound to Game's settings data through 0x28bf30; the controls object retains its own control-edit state. Their placement directly under the principal root, rather than below the gameplay container, permits the inspected frontend and system paths to activate them without creating another owner. The frontend menu widget at Game+0x128, constructed through 0x2910c0 under its main-branch child scene at Game+0x120, is a further distinct widget and should not be confused with these panel pointers.

The system menu's concrete callback at 0x292300 first clears its own associated scene's active state, then dispatches using its stored hovered choice. Options reaches 0x103110, which toggles the scene of interface+0x538; Controls reaches 0x102ed0, toggling interface+0x540. Start Menu reaches Game transition 0x9fdf0, and Exit Game reaches 0x9f660. These are activation/transition edges on existing objects. The frontend left-release handler 0x965e0 also has a menu-choice branch which activates the already existing options panel at Game+0x650. None of these scoped panel-opening paths constructs a new UI owner or replaces owner+0x140.

Per-frame interface update 0x103200 supplies an explicit frontend/gameplay exclusion gate. It reads the active states of the five frontend branches at interface offsets zero, +0x18, +0x58, +0x80 and +0xe8. It sets gameplay container interface+0x108 active only when all five are inactive. Thus active title/character/world frontend branches normally exclude the gameplay descendant branch through scene ancestry; the inventory widget's own active flag alone does not establish input reachability. Other derived active-state updates, including a shared Back control and mirrored companion-widget visibility, are also made in this routine. This is an observed scene gate, not a universal assertion that every invisible or modal object is excluded from every input route.

The source binding interval is also per-frame, not merely a UI-constructor operation. The only direct call to 0x103200 in the supplied call records is frame 0xa5a50 at 0xab5ce. Within that routine, inventory widget+0x1e8 is assigned the current actor's inventory header at actor+0x9f0, reached through Game+8 and World+0x448. Crafting widget+0x1e8 is assigned Game+0x17a8, and shop widget+0x1e8 is assigned Game+0x1870. These assignments are reached as part of the inspected normal interface-update body, independently of each widget's own shown/hidden state. They follow the interface's initial construction; those widget constructor slots begin null. The inventory binding can consequently be refreshed when the current actor path changes, while the crafting/shop bindings identify headers within the same Game allocation. These are borrowed header addresses, not deep copies of row buffers or a guarantee that earlier input has already seen a binding for the next actor state.

At the end of 0x103200, the same owner from Game+0x20 is passed to 0x349cf0 for its normal update. Initial interface setup also calls 0x340d60 and 0x333820 on the same owner/root. The inspected 0x333820 recursively establishes scene event-target pointers from a scene's own widget or inherited parent event target. The actual input path likewise reads the same owner: 0x94900 invokes interface dispatcher 0x101020, which obtains Game through interface+0x5c0 and the UI owner through Game+0x20. Left-down dispatcher 0x340ec0 ordinarily hit-tests from owner+0x140 and traverses that root for its visitor work. Selection transitions do not choose a separate frontend owner for this dispatch.

Ordinary hit-testing 0x333f60 requires an active scene state, clear scene flag bits two and twelve at +0x80 and its additional geometry/subtree conditions. Ordinary shared traversal 0x33c360 requires active state and clear flag bits two and one. Direct listener invocation additionally checks the event-target widget/listener and widget enable byte +0x1a0 as appropriate to the listener. Internal capture at owner+0x168 can supply a scene before a fresh root hit test; therefore a changed ancestor visibility value is not by itself proof that all captured input is impossible. Windows SetCapture is a separate mechanism from that UI pointer slot. Full capture, modal, focus, virtual override and disabled-state writer coverage is outside this contract.

Existing-character selection 0x9f7c0 deactivates the character-selection branch at Game+0x130. Its valid-character path loads the selected actor through 0x9bb20, invokes crafting-root replacement 0x107690 and rebuilds the crafting collection through 0xb2180. Its separate new-character path activates Game+0x170 and initializes the creation preview rather than replacing the principal input root. New-character completion 0x9ea10 deactivates Game+0x170 and performs actor/character-list work followed by interface list refresh 0x107440 and crafting-root replacement 0x107690. The observed successful saved-character branch in Game constructor reaches that same crafting-root replacement after the initial UI construction. These paths use the existing Game, owner pointer and frontend/gameplay scene branches; no direct owner construction or owner+0x140 replacement is present in their inspected bodies.

Reuse of the principal root does include real descendant recreation. Refresh 0x107440 detaches and later reattaches existing Select/Delete controls, clears and rebuilds children of the existing character-selection branch and repopulates its list. Routine 0x107690 constructs replacement crafting tab scenes and registers them through 0x280440, whose reached removal/attachment paths delete old tab-area children and attach new ones. The character-creation preview also changes actor and appearance state without rebuilding the principal input root. Consequently owner/root pointer continuity must not be treated as continuity of every button, tab, scene child or listener allocation beneath it.

The concrete return-to-title path is Start Menu callback 0x292300 reaching 0x9fdf0. That transition performs save/disconnect work, activates the existing main/title branch at Game+0x118, clears Game+0x420 and Game+0x668 and deactivates the inspected inventory, crafting, shop and other gameplay panels. Its disconnect helper 0x911e0 handles socket/thread state and can show an existing notification widget; it does not construct a new UI owner in its inspected body. The next ordinary 0x103200 update derives gameplay-container inactivity from the reactivated frontend branch. This transition does not call 0xf9ac0, 0x339b70 or 0x38e100 in the inspected direct paths and does not directly replace Game+0x20 or owner+0x140. It is reuse with state changes, not an authenticated total reset of all caches, listeners, hover or capture slots.

Ownership is broader than scene ancestry. Common object constructor 0x3669c0 records the owner and registers the object; scene/widget construction reaches that base path. Resource templates and detached scenes can therefore share the owner while being outside the principal input-root child tree. Ordinary Game destruction 0x818d0 destroys the inline interface through 0x82340 and the other Game-owned data but does not free the external Game+0x20 owner as part of that interface cleanup. The original shutdown sequence in 0x1355a0 deletes Game, renderer, world map and World before deleting the global UI/graphics owner. This demonstrates that the supplied owner outlives the Game in that shutdown path; it does not grant arbitrary borrowed scene pointers a lifetime beyond their individual deletion.

The concrete owner deleting entry is 0x38e700, identified from the original vtable at 0x480408. It calls 0x38e420, which reaches common UI cleanup 0x33a440, then frees the owner allocation when the low deletion-flag bit is set. Common cleanup releases UI resources and registered storage and reaches 0x33a860, which invokes deleting entries for remaining registered objects and frees their registry nodes. This bounds the ordinary owner/root lifetime by owner teardown, while 0x33dda0 separately demonstrates individual scene removal/deletion during normal descendant replacement. The constructor-created root is owned within that UI object system; Game's pointer does not represent independent ownership of a second root allocation.

The frame call at 0xab5ce is inside the observed World+0x3c8 interval entered through 0x2abb70 at 0xa6464 and left through 0x2b9890 at 0xadb23. Character selection 0x9f7c0 also has its own observed World lock interval. Other transition/panel callbacks and individual UI removal operations have different local boundaries; no common universal World/UI lock or total input-thread serialization follows. The bounded evidence supports continuity of the shared input owner/root across the named ordinary transitions, concrete branch attachment/exclusion and periodic source rebinding. It leaves graphics/device recreation, indirect root writers, complete teardown ordering for every failure, complete capture closure and concurrent lifetime guarantees unresolved, and prescribes no replacement implementation or capture policy.
