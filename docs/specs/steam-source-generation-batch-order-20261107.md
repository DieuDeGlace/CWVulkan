The client calls the shared sorter at RVA 0xF0790 from 0x855A1; the host calls it from 0xF2C7A. Both sort the complete collected candidate vector before shortening it. The comparison reads only the signed 32-bit priority at record +8 and orders smaller values first. There is no coordinate, insertion ordinal, resident-map order or centre identity comparison when priorities are equal. RVA 0xF0070 is the insertion-sorting path reached when the entire input contains at most 32 records. Its strictly-smaller moves preserve input order between equal priorities. For these small complete vectors, the tied coordinates therefore retain the ascending X-then-Y collection order proved above.

For larger inputs, that stable-tie conclusion does not hold. The sorter uses the record-moving partition routine at RVA 0xF0450, whose equal-priority handling includes nonadjacent exchanges. Pivot sampling at RVA 0xEF370 uses the first, middle and last records for partition sizes from 33 through 41, and three spaced triples for sizes of at least 42; the sample-ordering helper at RVA 0x76C20 still compares only priority. Partitioned subranges of at most 32 use the insertion path, but that does not undo earlier equal-record movements. The exhausted partition-budget path uses the heap helpers at RVAs 0xF02C0, 0xF06B0 and 0x7A770, also without a coordinate tie-break; the heap descent chooses its right child when the two child priorities are equal. The supported conclusion is an ascending priority sort with input- and path-dependent equal-priority record order for larger vectors. It is not a general stable ordering or a global lexicographic tie rule. No particular runtime tie permutation was captured or asserted here.
