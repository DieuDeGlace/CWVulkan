# Native interface visibility and capture cancellation

This bounded contract is FINAL / STABLE / HELD following full author readback. The supported original is cubeworld.original.exe.unpacked.exe, AMD64 PE32+, image base 0x140000000, 5,757,952 bytes, SHA-256 7AF18CB28C8BF848F355287428C6390B2EA2A682CA466190F5EB9859C5D6F244. Evidence comes from the original image, native decompilations including the longer-budget frame body, assembly.txt, calls.csv and function ranges after the standalone author policy. All addresses below are RVAs. The audit covers the ordinary F4 toggle, the identified render and pointer paths, and the original window procedure's explicit message handling.

Game+0x20 points to the UI owner. The owner's +0x140 points to the principal scene named root, created by 0x339b70 through 0x33cd30. The scene points to its style at scene+0x68. The style constructor 0x3736c0 creates a property named visibility with initial entries of one. The active visibility value is a 32-bit entry in the array at style+0xe0, indexed by the signed 32-bit selector at style+0xac. Predicate 0x9af00 reads the selected entry and treats any nonzero value as visible. Helper 0xa3a20 writes a Boolean value to this same property on whichever scene it receives. The principal scene's visibility, the visibility of individual descendants, and the existence of the root pointer are separate state.

The concrete F4 binding is the Windows key-down route. Window procedure 0x133c70 handles message 0x100, forwarding the low 16 bits of the key value to UI key handler 0x340df0 at 0x133da4, then the low 8 bits to Game handler 0x96e70 at 0x133db3. In that Windows virtual-key route, value 0x73 is F4. At 0x96fc3 the Game handler selects Game+0x20's owner+0x140, then reaches the toggle at 0x96efd. The visibility entry becomes one if it was zero and zero otherwise. The write occurs before the later gameplay and UI state tests in 0x96e70. The inspected key-down path performs this switch on each delivered key-down and has no repeat-bit filter in front of the toggle. The key-up route through 0x340e60 and 0x97870 updates key state. The visibility writer belongs to key-down.

The toggle's direct store affects the one visibility entry. It preserves the root pointer, child scene values, owner's internal capture at +0x168, last-move scene at +0x160 and held-button field at +0x1a8. The preceding 0x340df0 path also records the key in owner state and can invoke an enabled key target at owner+0x170 through virtual +0xc0. Effects of arbitrary indirect key targets are outside the direct visibility-store finding.

The ordinary draw traversal 0x330b20 rejects an inactive root on entry before drawing that scene or recursing to its descendants. The reached frame path runs 0xe2e00 with the renderer at Game+0x18. Renderer constructor 0xc3150 installs vtable 0x4385e8 and retains the same UI owner at renderer+0x540. Renderer slot +0x10 reaches 0xc4af0 and the owner draw entry 0x33e170, which traverses owner+0x140 through 0x330b20. Frame 0xa5a50 also samples root visibility through 0x9af00 before rendering. It adds mask 0x20 to the renderer's flags when the root is hidden. In 0xe2e00 this flag suppresses the additional branch containing 0xe64b0 that otherwise also requires a nonnull World+0x210 value. The later slot +0x10 dispatch remains present. Root visibility therefore has both a direct scene traversal effect and a separate renderer flag effect in this frame path.

Frame interface update 0x103200 remains a distinct call before renderer submission. It evaluates and writes individual child scene states, then reaches 0x349cf0 and the root scene update through 0x3358e0. In this ordinary update 0x3358e0 supplies zero for the override argument to 0x335920, whose active-state gate can skip the hidden root's scene update subtree. The update call and a subtree visit have different conditions. Child visibility can still change through Game-side code before that traversal.

Fresh root picking through 0x333f60 checks root visibility before visiting children. Its ordinary query also has scene flag and geometry gates. A hidden root yields no fresh scene from that traversal. The owner helper 0x33f1e0 takes a different route when +0x168 already holds a scene. It returns that pointer directly and otherwise performs the root pick. The normal down, up and movement dispatchers likewise prefer an existing capture scene. Capture can therefore route a direct event to a scene while root picking yields no result. This path uses the captured scene's event target at scene+0x78 and remains subject to the target's enabled state and the individual listener's flag checks. Root-wide visitor passes still check root activity.

Left down is admitted by 0x133c70 on message 0x201. It calls Windows SetCapture on the HWND at 0x133deb before invoking Game 0x94900 with index zero at 0x133dfa. The Game handler calls interface 0x101020, which reaches 0x340ec0 for that index. There is no principal-root visibility gate before this chain in the inspected path. The UI dispatcher sets bit zero in the 32-bit held field at owner+0x1a8 before choosing a capture scene or attempting a fresh pick. With a hidden root and an empty capture slot, the pick supplies no direct target. The dispatcher's press and focus bookkeeping still runs where applicable. With a captured scene, an enabled target can receive virtual +0x58 followed by listener tag two if the listener gates pass. Later Game-side behavior has its own conditions.

Left up on message 0x202 calls Windows ReleaseCapture at 0x133e0c before Game 0x965e0. The Game handler can first act on the active title branch and its cached menu selection, then reaches 0x101120 and 0x3410e0 for index zero. These checks and the interface call use their own state and have no direct test of principal-root visibility. UI up clears the left-held bit before resolving capture or fresh pick. Its enabled target virtual is +0x60, followed by listener tag three when admitted. For example, the ordinary Button vtable at 0x47b3a0 maps that virtual to 0x36a240. This handler reaches 0x3493b0, which clears owner+0x168 and redispatches move at the current coordinates, then clears the button's separate held byte at widget+0x2b8. A hidden principal root by itself does not prevent this release on a still enabled captured target. If the target virtual is ineligible, the owner's left-held bit still clears in 0x3410e0 and the Button release side effects are conditional on some reached cleanup path.

The HWND capture operation, the UI scene pointer and the held fields have different writers. Setter 0x33c410 writes only owner+0x168. Ordinary Button down 0x36a140 supplies its associated scene to that setter and sets widget+0x2b8. The HWND calls happen in the window procedure before Game mouse handlers and do not themselves run either Button virtual. A separate scene removal edge in 0x33dda0 clears owner+0x168 when the scene being removed is the captured scene, redispatches a move, and clears owner+0x160 if the removed scene matches that slot. The visibility toggle leaves the scene in place and does not reach scene removal. Neither 0x3493b0 nor this direct matching-scene clear synthesizes a button-up bit transition. The UI down/up dispatchers write the held bits separately.

Cursor input uses another gate. In main loop 0x1355a0, the initial client cursor sample at 0x136513 is used for cursor positioning. A later foreground check at 0x136638 compares GetForegroundWindow to the Game HWND. The branch which fails that guard skips the subsequent device polling and move work. The later absolute cursor poll at 0x1367f2 uses 0x1014f0 on the inline Game interface at Game+0x118. This predicate checks individual title, character, world, inventory, crafting, shop and other panel states and related flags. Its inspected body does not read principal-root visibility or the UI capture slot. When this predicate admits the absolute sample, the loop can convert the cursor position with ScreenToClient and reach Game move 0x97880 at 0x13683e. That handler independently uses the same interface predicate before routing through 0x101160 to 0x3418d0. A child state that remains active can thus admit cursor movement while F4 has hidden the principal root. Capture alone does not satisfy this polling predicate. Movement that does reach 0x3418d0 updates owner coordinates and uses capture first, then a fresh root pick if needed.

Window message 0x200 returns through 0x133c70 without a call to this UI move dispatcher. The frame also has a direct move call at 0xab1a1, on the separate branch where both Game bytes +0x668 and +0x1958 are nonzero. That branch uses Game dimensions and scale-related state to supply coordinates. The root visibility check used later for rendering is independent of this alternate move branch. The foreground guard bounds the described main-loop polling interval and does not itself clear capture or synthesize a release in the inspected branch.

The observed focus and cancellation messages are bounded by the registered window procedure 0x133c70. Its explicit 0x07 and 0x08 paths, WM_SETFOCUS and WM_KILLFOCUS, return one with no direct UI held, capture or hover changes. WM_ACTIVATE at 0x06, WM_ACTIVATEAPP at 0x1c, WM_CANCELMODE at 0x1f, and WM_CAPTURECHANGED at 0x215 reach the default tail to DefWindowProcW at 0x133ccf. The original body has no explicit call to UI up or to 0x3493b0 on those message cases. The default procedure's own Windows behavior is outside this native image. In particular, a Windows capture loss does not establish that the original code has cleared owner+0x168, owner+0x1a8 or a widget's held byte. This is a finding about the inspected handlers and foreground branch. Other window procedures, device paths and indirect callback effects were not closed.

There are separate verified child-panel hide paths. Right down through 0x101020 first dispatches its right-button path, then uses 0x33f1e0. On a null result it clears the interface flag at +0x308 and the scene visibility entries for the objects at interface+0x218, +0x228 and +0x230. This is a panel state change reached from the right-button handler, distinct from F4's principal-root store. Frame 0xa5a50 also has a conditional branch before 0xab1a1 that clears multiple panel visibility values through 0xa3a20. The direct visibility stores in these paths do not clear the UI capture slot. Their additional callers and callbacks have separate effects.

The original Start Menu return is concrete. System menu draw 0x291e00 labels the third entry Start Menu and registers 0x292300 under listener tag three. That callback clears its own associated scene's visibility, then the selected Start Menu case reaches 0x9fdf0 at 0x29234c. The transition reaches save and disconnect helpers 0xa27b0 and 0x911e0, activates the title scene pointer at Game+0x118, clears Game+0x420 and +0x668, and deactivates the reached inventory, crafting, shop and other gameplay panel scenes. On the ordinary later 0x103200 update, the active title branch is one of the frontend states which cause gameplay container Game+0x220 to be set inactive. The direct transition body does not write the principal root's visibility entry, HWND capture, the UI capture slot or held bits. If this callback was reached during normal Button release, any reached capture cleanup is attributable to that earlier up virtual and its own conditions. The audit leaves indirect transition-side effects, other root visibility writers, lost-focus cleanup outside the named paths and arbitrary captured-object lifetimes unresolved.
