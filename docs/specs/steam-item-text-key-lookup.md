# Steam item text-key lookup

This bounded native-only note supports cubeworld.original.exe.unpacked.exe, 5,757,952 bytes, SHA-256 7AF18CB28C8BF848F355287428C6390B2EA2A682CA466190F5EB9859C5D6F244, preferred image base 0x140000000. Addresses below are RVAs. Evidence was restricted to that image and its original functions, retry-180-phase1 functions, assembly.txt, calls.csv, and function_ranges.csv after reading the standalone native-author rules. No other project prose, implementation, SDK, tests, probes, owner outputs, or runtime execution supplied facts. The scope is the numeric-pair-to-text-key lookup, not complete localization formatting or a complete resource-owner layout.

A minimal callable lookup is established at RVA 0x16af30. Its Windows x64 argument positions are owner address in RCX, caller-provided string-destination address in RDX, first 32-bit numeric key in R8D, and second 32-bit numeric key in R9D. Normal return places the same destination address in RAX. The first two arguments are addresses; the latter two are values. This entry receives no full item-record pointer, and its own body does not inspect an item record or normalize item fields.

Native callers establish the relationship of these values to item data. RVA 0x15e710, at callsite 0x15e75e, zero-extends the byte at item+0 into R8D and loads the 32-bit field at item+4 into R9D. RVA 0xa5a50, at callsite 0xac6a6, obtains the corresponding byte and 32-bit field from an inventory element containing an item value, then passes them separately. Thus category and subtype in this note refer specifically to the item byte at +0 and the 32-bit secondary identifier at +4. The lookup itself compares both numeric arguments as signed 32-bit values, even though the demonstrated first input originated as an unsigned byte. No complete taxonomy, permitted-value range, or SDK enumeration is inferred from those uses.

The returned value is used as a resource key. RVA 0x1628b0 calls this lookup at 0x162dbe and passes the returned string object to RVA 0x16c750 at 0x162dc9, which searches the owner's separate keyed-resource structure at owner+0x98. Direct Game callers also pass the lookup result to RVA 0x16be20 for subsequent resource processing, for example after callsites 0x8e950 and 0xac6a6. Consequently this operation retrieves the identifier text stored for the numeric pair. It does not by itself construct the full displayed item name, choose all item-name modifiers, or complete localization. Exact vocabulary, prefixes, file origins, and character restrictions for the stored keys were not established by this bounded lookup audit.

For the ordinary Game caller path, RCX receives the address Game+0x50 directly. The original instructions before 0x8e950 and 0xac6a6 calculate that address without loading a pointer from the +0x50 field. Constructor RVA 0x7ea80 calls RVA 0x1510f0 on the same inline subobject address. Here Game is simply the base address used by those observed native caller objects, without assuming a reconstructed class declaration. Successful lookup additionally depends on the owner's initialized table and its live nodes and strings; the address relationship alone is not evidence that arbitrary storage at that offset is ready for lookup.

The table read by RVA 0x16af30 is anchored by an eight-byte pointer at owner+0x58. This pointer denotes a head or sentinel node. The lookup starts from the eight-byte root link at head+8. For a visited node, byte +0x19 is the sentinel marker: zero identifies a traversed ordinary node, and nonzero stops that traversal. The child links read by this entry are eight-byte addresses at node+0 and node+0x10. The observed numeric key fields are signed 32-bit integers at node+0x20 and node+0x24, in that order. The associated string object starts at node+0x28. These are the offsets actually consumed by the entry; total node allocation size, balancing metadata, mutation procedures, and other links are not specified.

The ordering is signed lexicographic ordering of the two numeric fields: the first field decides order unless equal, then the second decides it. Both the traversal and the final candidate comparison use this relationship. The returned value requires an exact numeric-pair match. A neighboring entry in the ordering is not a supported fallback. Empty trees and absent pairs take the same result-construction branch. The entry assumes valid linked native structures; it supplies no null-table, corrupt-link, cycle, or node-lifetime recovery contract.

On a match, RVA 0x16af30 constructs a copy of the complete string at node+0x28 through RVA 0x3d3b0, with source position zero and the maximum requested substring count, which that helper clamps to the source length. On absence, it constructs an empty wide string through RVA 0x3d4f0 with character count zero. RAX still returns the destination address. There is no separate Boolean found flag, no returned table-node address, and no "unknown" literal in this entry's absence branch. An existing entry whose stored string is empty is indistinguishable from absence by output characters alone.

The destination occupies 0x20 bytes. Its first 0x10 bytes hold either an inline buffer or a heap-pointer representation. At object+0x10 is an unsigned 64-bit length in 16-bit character units, excluding terminator; at +0x18 is an unsigned 64-bit capacity in the same units, excluding terminator. Capacity below 8 selects inline character storage at the object address. Capacity of 8 or greater selects the buffer pointer stored at object+0. A two-byte zero terminates the logical character range. This is the original Windows wide-character representation, with two-byte little-endian units rather than narrow bytes or UTF-8. Well-formed Unicode, Unicode normalization, and display-character counting are not established properties of every table value.

Both match and absence branches initialize destination capacity to 7, length to zero, and the first wide unit to zero before invoking their copy helper. The original caller supplies temporary storage; no preexisting character buffer or destination allocation is needed for the shown construction. This entry does not first free an old destination heap allocation before overwriting those fields, so its observed behavior is construction into fresh or previously disposed storage, without established ownership-preserving assignment to a live result. Arbitrary overlap between destination and owner or source-string storage is outside the demonstrated native use.

The output owns its copied characters. A successful heap result is not a borrowed pointer into the table, and the source node is not transferred to the caller. Once normal copying finishes, disposal of the result concerns that result's own representation. Original callers consume then clean up their temporary result, for example RVA 0xa5a50 destroys the lookup result after subsequent resource processing, and RVA 0x15e710 conditionally deallocates a returned heap string. Mutation, movement, or destruction of the result can invalidate a character address extracted from it. A bytewise copy of a heap-bearing result is not shown to allocate a second independent character buffer.

The callable wide-string cleanup entry is RVA 0x15c9a0, receiving the string-object address in RCX with no meaningful return value. For capacity at least 8 it calls wide-buffer deallocator RVA 0x33b10 using the object address in RCX, heap-buffer pointer in RDX, and capacity plus one in R8. It then restores capacity 7, length zero, and the first inline wide unit zero. The caller-owned 0x20-byte object storage is not freed. The lower-level deallocator interprets the allocation count in two-byte units including terminator space and validates the original aligned-allocation metadata for allocations whose byte size reaches 0x1000. It is not the object cleanup operation for an inline result. Invalid metadata can terminate through the runtime invalid-parameter path.

The pair presented by full item-name formatting is not always the pair in the caller's original item bytes. RVA 0x1628b0 first invokes RVA 0x1092b0 to copy and normalize its item input. In that copy, category 0x16 with secondary value 0x3f becomes category 3 with the secondary value taken from item+0x18. Secondary values 0x40, 0x41, and 0x42 under category 0x16 become categories 4, 8, and 9 respectively, each with secondary value zero. The direct lookup RVA 0x16af30 performs none of those changes. This establishes a difference between raw-pair lookup and that higher-level caller's normalized route. A separate full-item-to-key-only entry with identical scope was not established; RVA 0x15e710 receives an item pointer but also performs additional processing beyond this minimal lookup.

The inspected lookup body reads the owner table and constructs the destination; it does not insert an entry, directly mutate the table, select random alternatives, call imported rand or srand, or acquire the World critical-section helpers. Reached string copying can allocate through RVA 0x334f0 and allocator RVA 0xce180. Length-error, allocation-failure, and runtime invalid-parameter paths exist in the string helpers. Normal fallback to empty text is therefore not a guarantee of recovery from malformed structures, invalid addresses, allocation failure, or every exception. Destination state after exceptional execution was not established.

There is concrete caller-held protection on some routes. RVA 0xa5a50 enters World+0x3c8 through RVA 0x2abb70 at 0xa6464 and releases it through RVA 0x2b9890 at 0xadb23; the World address is obtained from Game+8. Its direct lookup at 0xac6a6 and shown consumption and cleanup occur inside that normal-path interval. The route into RVA 0x8ae50 from 0xa9b2c also lies within that interval and contains lookup callsite 0x8e950. The two helper bodies establish operations on the inline critical section at the supplied World address plus 0x3c8. The lookup does not acquire that protection for itself.

This caller evidence neither identifies every resource-table writer nor proves that the World section protects the Game's resource table, all nested strings, or owner shutdown. Full protection inherited by every other caller, every runtime-internal lock, mutation/publication rules, and a whole-program writer or lock census remain unresolved. No replacement table representation, implementation strategy, capture policy, universal lock order, or quiescence requirement follows from this note.
